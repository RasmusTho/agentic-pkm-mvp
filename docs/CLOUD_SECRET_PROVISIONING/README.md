# Cloud Secret Provisioning

## Outcome

Provide Linux channel VMs with centrally administered Bitwarden Secrets Manager (BWS) secrets. Preserve the existing macOS Keychain path for Mac-hosted processes. Keep channel and consumer grants explicit and fail closed before runtime or deployment mutations. Secret values and machine-account tokens stay out of command arguments, output, logs, receipts, Git, BuilderOps records, iCloud, and admin/deploy orchestrator environments. Values reach runtime consumers only through their declared owner-controlled handoff; PostgreSQL credentials use file-backed Compose secrets.

The 2026-09-24 owner decision in #5667 selects BWS, two projects named prod and non-prod, and exactly three machine accounts: non-prod-reader shared by ygg-dev and ygg-test, prod-reader for ygg-prod, and admin for writes. The admin token remains in the agent host Keychain. This specification does not provision the account, organization, projects, accounts, or live VMs.

This is boundary work. Yggdrasil Platform and Operations owns Linux host and Compose lifecycle. Product/Runtime owners retain authority over Heimdal key semantics and database use. Builder System tooling may administer secrets through the approved admin identity, but it does not become a secret store or runtime authority.

## Current status

The repository currently implements the Mac Keychain path. This specification defines the Linux BWS target and does not claim live VM qualification. Existing host credential files remain until a separately authorized operator migration; code delivery alone does not remove or rotate live host material.

A decision is still required for production Heimdal raw-store-key rotation. The current raw record format has one configured AES key and no key identifier or multi-key read path. Changing the current value would make earlier ciphertext unreadable. Until the owner records the policy on #5667, the implementation must refuse protected data-key rotation and must not infer approval from an environment or command flag. Heimdal archive-pass is also protected because it encrypts an existing archive volume.

Live shared-copy parity also has an explicit owner gate: the local controller lock coordinates only cooperating commands on one host. The owner must approve one designated BWS admin writer and provide live evidence that its admin credential is unavailable outside that controller, or adopt a shared fencing mechanism. Keep deployment admission blocked until that gate passes.

## Fixed constraints

1. The active identity is shared/<logical-secret> for openai.api-key, anthropic.api-key, github.token, and discord.webhook, and <channel>/<logical-secret> for heimdal.raw-store-key, heimdal.archive-pass, and postgres.password. The shared identities are the narrow exception to per-channel value separation approved by the owner in #5667: each externally issued provider value is mirrored in prod and non-prod, so a non-prod project reader can retrieve the same provider value used by prod. No other secret uses a shared identity. BWS import updates the store only and does not create or rotate provider credentials.
2. Existing consumer grants remain code-enforced environment bindings. BWS item identity is not per-consumer authorization. The only additional non-environment route is required, channel-scoped `postgres.password` delivered as a file, with non-secret `POSTGRES_PASSWORD_FILE` for Compose `db` and `DATABASE_PASSWORD_FILE` for the five application/migration services; no password environment binding is added. The closed map is `postgres-db` -> `db`, `postgres-migrate` -> `migrate`, `postgres-api` -> `api`, `postgres-worker` -> `worker`, `postgres-watcher` -> `watcher`, and `postgres-capture-watch` -> `heimdal-capture-watch`, for dev/test/prod only. Normal database deploys require the selected password before any remote deployment-state mutation and recheck it on the VM before local mutation and Compose. The explicit first-initialization exception is defined in Fixed constraint 15.
3. Project selection is fixed: dev and test use non-prod; prod uses prod. Read-only machine accounts are project-scoped. A non-prod request must not reach the prod project.
4. Linux selects BWS explicitly and fails closed if BWS is unavailable. It never falls back to macOS Keychain. Mac-hosted processes keep using Keychain.
5. A secret check takes the exact consumer set selected for the requested runtime/deploy operation and evaluates only those consumers' declared bindings. An absent optional binding may be skipped; every present selected value must pass its grammar, including optional values. An inactive consumer is not checked and does not block an unrelated deploy. A missing required binding, malformed present value, or divergent selected shared value fails. Failures name logical identifiers and status only.
6. Secret values and machine-account tokens do not appear in argv, stdout, stderr, shell traces, rendered Compose output, admin/deploy orchestrator environments, logs, receipts, Git, BuilderOps, or iCloud. Runtime exposure follows the existing per-consumer contract. PostgreSQL passwords are not placed in Compose values, the deploy orchestrator environment, application environments, or PostgreSQL server-process environments. Governed-channel `DATABASE_URL` and `DB_DSN` overrides must be credential-free: reject a URI password or keyword-DSN `password` value before it enters Compose or an application environment. Credential-free overrides may supply non-secret connection fields; the PostgreSQL password still comes from the file-backed secret. On every startup, including for an initialized data directory, the official PostgreSQL entrypoint reads POSTGRES_PASSWORD_FILE into its own short-lived startup shell before checking initialization state. On an empty data directory, the upstream entrypoint starts a temporary initialization server through `pg_ctl` before its final POSTGRES_ cleanup; BWS-04 must scrub `POSTGRES_PASSWORD` and `PGPASSWORD` from the `pg_ctl` child environment and separately scrub both from the shell environment immediately before the final steady-state `exec` on every startup path, including initialized data. Only the short-lived entrypoint or initialization-client access needed to initialize the role may retain the value. The VM-side BWS reader runs under a repository-managed systemd unit or drop-in with `LoadCredentialEncrypted=bws-machine-account-token:<encrypted-current-source>` and `BWS_ACCESS_TOKEN_FILE=%d/bws-machine-account-token`; the runtime path is `$CREDENTIALS_DIRECTORY/bws-machine-account-token`. BWS-01 reads the token from that file only, never from a token-valued environment variable. A missing or unreadable credential fails before a provider request or deploy mutation. BWS-03 installs the encrypted source atomically and does not modify a live unit.
7. BWS read responses can contain secret values. The reader may hold a response in memory only long enough to select, validate, or compare values for the requested consumers; it emits no raw provider response.
8. Admin writes use an authenticated request-body interface. Import accepts an externally issued or already-active value only from standard input; it never places the value in argv or echoes it. The BWS CLI create/edit syntax places values in argv and default responses include values, so those forms do not meet this contract. BWS import does not create, revoke, or claim to rotate a provider-side credential; issuer-side rollout and overlap remain external operations.
9. Admin writes persist both target project pre-states before changing either shared copy: snapshot a present value or append a value-free `previous_state=absent` tombstone for an absent copy. The protected local append-only history backend is chosen by BWS-02, but a history write counts as durable only after its flush/fsync-equivalent commit returns. Each paired operation has a non-secret operation ID and a durable prepared record before the first BWS write. Put a machine-readable non-secret operation marker in each BWS item note while preserving owner note text; the marker correlates a successful write but is not an idempotency or fencing token. A provider success/matching marker proves that target applied; only a typed response guaranteed to reject before commit proves no effect. A lost acknowledgment, process death after send, absent marker, mismatched readback, or unavailable readback is indeterminate and does not prove the request cannot still land. While any send is indeterminate, keep the journal pending and do not compensate, retry, start a fresh import, check selected BWS values, or deploy. If BWS exposes no authoritative terminal status for that request, remain blocked; do not invent one from a missing marker or local timeout. After every sent request has an authoritative terminal result, append a terminal history record; compensate only confirmed committed targets to their recorded pre-state under the same exclusive lock, or reconcile a shared import with a fresh stdin value and current-state snapshots/tombstones. Never replay stale compensation over a later import. Other operation kinds use their own durable matching-receipt contracts: token push remote journal, empty-database bootstrap item metadata plus terminal provider outcome, or deploy remote journal. Checks and deploys fail closed until a matching terminal receipt is durable. No task deletes history automatically.
10. Rotation or deletion of protected Heimdal data-encryption secrets remains blocked until #5667 records an owner decision and an approved behavior is specified. The PostgreSQL password must match the existing initialized database role: importing its current value is allowed, but changing the BWS item alone does not rotate that role. PostgreSQL password rotation on an initialized data directory requires a separate coordinated database-role cutover contract.
11. The PostgreSQL password file is root-owned with mode `0440` and the configured database-client primary GID (`LOCAL_GID`); its parent tmpfs directory is root-only (`0700`). This gives the configured non-root application and migration UID/GID read access without granting host users directory traversal or world access. Grant the file-backed Compose secret only to PostgreSQL and the selected database clients. Local file-backed Compose secrets are bind mounts: Compose ignores secret `uid`, `gid`, and `mode` overrides, so prepare the source file's ownership and mode before mounting it ([Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/), [Compose service secret attributes](https://docs.docker.com/reference/compose-file/services/)). Keep the source present while any consuming container may restart or be recreated; a managed host lifecycle rehydrates it before every Compose start/recreate and after host boot, and removes it only after all consumers stop. Docker must not restart a consumer before rehydration. Exclude the source path from Git and cleanup receipts.
12. BWS plan limits are hard constraints: two projects and three machine accounts. Exceeding them is a design change requiring owner approval.
13. Live BWS setup, VM token installation, host cleanup, and channel qualification are operator actions. Repository tests and CI do not claim those actions occurred.
14. All supported BWS checks, admin writes, reader-token pushes, and channel deploy dispatches run through one designated agent-host controller and a stable owner-only local operation lock outside Git/iCloud. That lock serializes only cooperating entrypoints on that host; it cannot fence another host, direct BWS client, or an already-sent provider request. Before claiming shared parity is race-safe or live qualification is complete, the owner must approve the designated sole BWS admin writer and provide a live qualification receipt that admin credentials are restricted to that controller, with no second controller or out-of-band BWS writer and no direct VM deploy/secret-resolution bypass. If the owner cannot enforce this boundary, a shared/distributed fencing mechanism is required before qualification or deployment admission. Keep deploy admission blocked until one of those gates is satisfied. Lock order is agent-host operation lock first, then VM per-channel mutation lock; never acquire them in reverse. Persist a value-free operation ID, operation kind, target, and stage before external mutation; retain it until a matching terminal receipt is durable. After interruption, recovery must match the journaled operation ID to an authoritative terminal outcome: shared BWS import remains pending on an indeterminate provider send; token push and deploy require durable remote journal receipts; bootstrap also checks the locked empty directory and operation marker. A deploy worker on the VM, supervised independently of SSH, owns the remote lock through Compose completion and receipt write. Reconnect joins the same operation ID. If that worker ends without a receipt, a new worker cannot reconcile/admit work until the old worker/subprocess is gone and affected Compose/Docker resources are quiescent; if quiescence is unknown, remain pending. A VM lock snapshot or local lock release alone is not terminal proof.
15. Normal deploys require `postgres.password` to be present before any remote deployment-state mutation. The only absent-password exception is BWS-04 first initialization: under the agent-host operation lock, check all other selected identities, acquire the VM per-channel lock as a coordination-only action, and inspect the actual database data directory under that lock. If it is not empty, release the lock and fail without creating a BWS password or changing deployment state. If it is empty, BWS-04 alone may generate and persist one password after BWS-02 has durably recorded the value-free absence tombstone and prepared operation ID. Include that ID in non-secret BWS item metadata, read the item back, and verify it before any deployment-state mutation; then recheck it on the VM before local mutation and Compose. If interrupted after a create may have reached BWS, the same operation ID remains pending. A retry rechecks emptiness and reads the BWS item; exactly one matching item is read and reused. An absent or ambiguous readback leaves the operation indeterminate and must not trigger another create without authoritative proof the prior request did not commit. It does not silently start a new bootstrap operation or replace an existing item. An initialized database with a missing item must import its current role value and cannot use bootstrap.

## Cross-task invariants / interaction safety

- INV-BWS-1 — channel isolation: dev/test lookup is constrained to the non-prod project and prod lookup is constrained to prod. A failed or unknown channel resolves no project and never falls back.
- INV-BWS-2 — consumer minimization: the code contract decides which logical bindings a consumer can receive. BWS project access is a coarse outer boundary, not a substitute for the allowlist.
- INV-BWS-3 — value non-disclosure: tests assert successful and failing paths do not emit a canary value through output, logs, exceptions, argv, Compose configuration, or receipts.
- INV-BWS-4 — durable history before activation: BWS-02 writes a non-secret operation ID, both project pre-state snapshots/tombstones, and a prepared event to protected append-only history; the durable boundary is a completed flush/fsync-equivalent before any BWS value write. It appends a terminal record only after each sent provider request has an authoritative terminal outcome. An operation marker in an item note correlates success but does not fence or deduplicate a request. A lost acknowledgment, process death after send, missing/mismatched marker, or unavailable readback remains indeterminate: check/deploy stay blocked, and there is no compensation, retry, or fresh stdin import while the earlier request could still land. If the provider offers no authoritative terminal outcome, leave the operation pending. Once all sends are terminal, compensate only confirmed committed targets to a present snapshot or delete a previously absent copy, or reconcile with a fresh stdin import and current snapshots/tombstones. Other mutating operation kinds use their operation-specific journal/readback contracts in INV-BWS-15.
- INV-BWS-5 — serialized preflight and activation: every supported check, import, token push, and deploy uses the same exclusive agent-host operation lock. This local lock serializes cooperating entrypoints on one host only; it cannot fence another host, direct BWS client, or an already-sent provider request. A deploy holds it from before the host parity/selected-consumer check through the VM project-scoped recheck, secret materialization, and Compose activation receipt, so a cooperating admin import cannot interleave between parity check and use. Acquire this lock before the per-channel VM mutation lock. The owner-approved sole-admin-writer and live-credential-restriction gate in Fixed constraint 14 is required before claiming parity race closure or live readiness; otherwise use shared/distributed fencing. Direct VM bypass is unsupported. Pending operations after process/transport loss block new work until a matching durable terminal receipt; the project-only VM read alone is not a cross-project fence.
- INV-BWS-6 — mounted file lifecycle and access: the PostgreSQL password source is a root-owned `0440` file in a root-only `0700` tmpfs directory, with its group set to the configured database-client primary GID. The file-backed secret is mounted only into PostgreSQL and selected database clients; the actual non-root application/migration UID/GID can read it. Because file-backed Compose secrets are bind mounts and ignore `uid`/`gid`/`mode` remapping, enforce access through source-file metadata. The host lifecycle manager rehydrates before start/restart/recreate and cleans up only after all consumers stop; Compose returning is not a cleanup boundary.
- INV-BWS-7 — protected-key hold: while the owner decision is open, protected production-key changes are refused. A partial admin operation cannot change the active value before the policy gate.
- INV-BWS-8 — repository/live separation: a passing fake-provider test proves code behavior only. It does not assert that BWS accounts exist, tokens are installed, or a VM is healthy.
- INV-BWS-9 — shared-copy parity: the agent-host controller reads both copies under its local operation lock and verifies equality without disclosure. This lock coordinates only cooperating calls on that host. Claim parity safe for deployment only after the owner-approved sole-admin-writer/live credential restriction gate in Fixed constraint 14, or after a shared fencing mechanism is implemented. A project-scoped VM reader never reaches the peer. Partial write, crash, or unknown provider outcome stays pending/divergent and blocks checks/deploy; a note marker or absent readback is not a provider fence.
- INV-BWS-10 — consumer applicability: only required bindings for consumers selected by the deployment plan can block that operation. Optional or inactive model-provider credentials remain unprovisioned without blocking unrelated deployment; present malformed values still fail closed when their consumer is selected.
- INV-BWS-11 — database resolver consistency: application configuration, Alembic migration setup, and direct DB clients such as Heimdal raw-store access use one file-aware database resolver. No client bypasses the password file by reading `DATABASE_URL`/`DB_DSN` directly; credential-free DSNs provide only non-secret connection fields, and password-bearing DSNs fail closed.
- INV-BWS-12 — VM token credential binding: the repository-managed systemd reader unit/drop-in loads encrypted credential `bws-machine-account-token` and exposes only the path `$CREDENTIALS_DIRECTORY/bws-machine-account-token` through `BWS_ACCESS_TOKEN_FILE`; BWS-01 reads that file and fails before provider access or mutation when it is absent or unreadable. BWS-03 installs the encrypted credential without claiming a live unit update.
- INV-BWS-13 — database secret identity and authority: `postgres.password` is required, channel-scoped, and file-delivered with no environment binding. The host contract enumerates exactly the six authorized consumer/service pairs in Fixed constraint 2. Normal selected services are checked before remote deployment-state mutation and rechecked before VM mutation/Compose. Only Fixed constraint 15 permits a missing value, and only after a locked empty-directory first-init inspection.
- INV-BWS-14 — absent-copy history: first provisioning and missing-copy recovery append a value-free `previous_state=absent` tombstone for each absent target project/logical identity before any shared copy is updated. Present copies are snapshotted; history failure blocks all writes.
- INV-BWS-15 — coordinated controller admission: a single agent-host operation lock serializes cooperating secret and deploy entrypoints on that host; it does not fence other hosts or direct BWS writers. The owner-approved sole-writer/live-credential-restriction gate or shared fencing mechanism is required before live qualification. The operation journal survives process loss and forces operation-ID-matched, durable terminal receipts before admission resumes. Unknown provider writes remain pending and fail-closed. VM token push and deploy use value-free durable remote journals with terminal `committed`/`aborted` receipts; a VM-side deploy supervisor owns the lock independent of SSH, and recovery joins the same ID or proves the old worker and affected Compose/Docker resources quiescent. Lock state alone is not a receipt.
- INV-BWS-16 — first PostgreSQL initialization: absent `postgres.password` is accepted only after BWS-04 holds the channel mutation lock and proves the selected data directory is empty; the absence tombstone and prepared operation ID are durable before the sole initial BWS write. Existing data with a missing password fails before deployment-state changes. A retry with that pending ID rechecks emptiness and reads/reuses exactly one item carrying the same non-secret operation ID; absent or ambiguous readback stays pending and never issues a second potentially duplicating create.

Partial failure paths must preserve these invariants. If a history write or either pre-state record fails, no BWS value changes. A shared import retains history if a value write fails; it may compensate a confirmed changed copy only after all sent requests have authoritative terminal outcomes. A process interruption or unknown provider response leaves a durable prepared operation; after restart, checks and deploy stay blocked, with no compensation, retry, or fresh import until terminality is proven. If the provider cannot supply authoritative terminality, the operation remains pending. After all sends are terminal, a fresh authorized stdin import may record current pre-states, apply one common requested value, verify parity, then close the old operation; it never applies stale rollback over a later import. Bootstrap recovery is distinct: BWS-04 rechecks emptiness under the VM lock and, with the same pending ID, reads the item carrying that operation ID; a possibly sent create with absent/ambiguous readback remains pending without another create. Deploy writes a value-free remote per-channel journal with `operation_id`, channel, operation kind, stage, and terminal result. Persist each stage atomically (write temp, flush/fsync file, rename, flush/fsync parent directory) in an owner-only persistent VM path outside the repo and tmpfs: `prepared`, `preflighted`, `materialized`, `activating`, then `committed` or `aborted`. Persist `activating` before Compose. After successful activation, persist `committed`; that durable stage is the terminal receipt. Persist `aborted` only after confirming no deployment effect or completed rollback; its durable stage is the terminal receipt. A VM-side supervised worker keyed by operation ID holds the VM lock and is independent of SSH. Reconnect joins it. Recovery after worker loss proves no old worker/subprocess remains and no affected Compose/Docker transition is in progress before reconciling; if it cannot prove quiescence and terminal outcome, remain pending. The host clears its pending deploy operation only on a matching same-ID terminal receipt, never from lock release/snapshot alone. Token push likewise uses a durable remote same-ID journal/terminal receipt and per-channel lock; current-pointer readback without a terminal receipt is not sufficient to retry or report completion. A cooperating host lock alone does not prove there is only one BWS admin writer: do not claim parity safety or live readiness until Fixed constraint 14 owner qualification passes, or shared fencing exists. For normal DB deploy, missing required `postgres.password` fails before remote deployment-state mutation. First-init bootstrap is the sole exception in Fixed constraint 15. The VM recheck and lock-protected lifecycle preserve the selected file source through Compose activation and consumer restart/recreate; cleanup waits until every consumer stops.
