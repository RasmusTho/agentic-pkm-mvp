User Guide

Companion UI organizes Yggdrasil’s cognitive prosthesis functions into four user-facing modes: Find, Reorient, Resurface, and Act. These modes are product affordances over existing authority and contract boundaries. This guide assembles content from the canonical source docs — docs/COMPANION_UI_PRODUCT_SPEC.md and companion-ui/docs/COMPANION_UI_STATE_MAP.md.

Product Modes

Source: docs/COMPANION_UI_PRODUCT_SPEC.md — Mode Model

Each mode reduces a specific cognitive burden and routes to the appropriate authority surface (Panel / Chat / Automation). Modes do not replace authority sources.

Find Mode 1

“Where is the thing I need, and what is the best source to cite?”

Reduces manual recall, repeated search, and uncertainty about source quality. Each answer exposes source citations and an inspectable retrieval basis.

Authority limits: Find can present and summarize; it cannot promote retrieved material into durable knowledge without an explicit governed flow.

Primary surfaces: Chat · Panel

Current-state caveat: retrieval and related diagnostics are partially shipped; exact UX assembly varies by current runtime surface and flags.

Reorient Mode 2

“What was I doing, what changed, and what should I do next?”

Reduces interruption-recovery overhead and the cost of reloading situational context from scratch. The orientation bundle separates current frame, recent deltas, open loops, and confidence labels.

Authority limits: Reorient can synthesize and propose; it does not execute actions on its own.

Primary surfaces: Chat-first · Panel (handoff)

Current-state caveat: bounded orientation runtime seams exist, but full target-state orientation UX assembly is not yet baseline.

Resurface Mode 3

“What quietly important thing should return to attention now?”

Reduces missed follow-up, forgotten relevance, and re-orientation effort after attention drift. The baseline posture is pull/snapshot/read-only; ambient refresh is bounded foreground refresh only.

Authority limits: Resurface can suggest; it must not escalate to urgent-task semantics unless explicitly promoted. Resurfacing presence must not become approval, urgency, memory promotion, or write authority.

Primary surfaces: Companion orientation/resurface areas across Chat/Panel

Current-state caveat: minimal resurfacing runtime seams exist; full product-surface suggestion orchestration and durable dismiss/snooze/pin remain target-state.

Act Mode 4

“How do I turn intent into a governed, completed change?”

Reduces coordination overhead between deciding, executing, and documenting outcomes. The action flow preserves intent → propose → decide → execute → receipt and produces inspectable receipts.

Authority limits: Act must not bypass write guards; must distinguish propose, stage, apply, and log.

Primary surfaces: Panel · Chat (proposal/clarification) · Automation

Current-state caveat: parts of this flow are shipped across Panel/runtime contracts; broader unified Companion Act UX remains target-state.

Principles

Source: docs/COMPANION_UI_PRODUCT_SPEC.md — Companion UI Principles

  • Context must be inspectable.
  • Suggestions must be dismissible.
  • Writes must be staged before applied unless explicitly authorized by contract.
  • Chat is not source of truth.
  • Agent memory is not hidden authority.
  • Human-readable artifacts remain primary.
  • Cognitive-load support is central: reduce decoding, parsing, spelling, review, and resumption friction without simplifying away the human’s reasoning task.
  • Review surfaces should be verifiability-first: source and consequences stay reachable before an agent projection becomes a decision.
  • The UI should reveal enough system state to support trust without exposing unnecessary runtime machinery.

Authority and Safety

Source: docs/COMPANION_UI_PRODUCT_SPEC.md — Authority And Safety

Companion UI may

  • Present suggestions
  • Host human decisions
  • Display runtime state

Companion UI must not

  • Become a source of authority itself
  • Bypass contracts, write guards, or human decisions
  • Treat memory, chat output, or UI state as authoritative by default

Authority comes from

  • Contracts
  • Events and receipts
  • Write guards
  • Explicit human decisions
  • Owner docs
