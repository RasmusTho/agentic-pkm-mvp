Design Handoff Governance Pack

How a Claude Design exploration becomes a governed implementation input — without becoming architecture authority on the way. Defines the chain exploration → handoff package → normalized spec → GitHub issue → PR → validation receipt, the maturity bar between each link, the templates each step produces, and the disclaimers that keep design from being mistaken for runtime truth.

Pack: HANDOFF_GOVERNANCE Authority: Process pattern only — not runtime Owner-docs: INTERACTION_SURFACES_AND_AUTHORITY Status: Design handoff · v1 · 2026-05-14

01 ·Context & boundary

What this pack is for, and what it deliberately is not.

What this pack is

Yggdrasil already has a strong rule: design artifacts are not architecture authority, runtime truth lives in shipped code, tests, status docs, and validation receipts. That rule is healthy. It also means that every Claude Design exploration enters a system where it is, by design, not allowed to mutate truth on its own. This pack defines the intermediate path — the maturity bar, the templates, the affordances — so design work actually lands as governed inputs instead of accumulating as well-intentioned loose HTML.

Concretely, the pack covers five artifacts:

  • The governance flow diagram (§02) that names each link in the chain and what evidence crosses each boundary.
  • The maturity checklist (§03) that decides when an exploration is allowed to become a normalized spec.
  • The review console prototype (§04) — a single operator surface for walking explorations through the chain.
  • Three templates (§05–07): README, implementation-contract notes, authority boundaries.
  • The state, edge-case, and influence inventories (§08–09) that every design must answer before promotion.

Surface boundaries we are honoring

  • Repo docs & contracts remain architecture authority. This pack governs process, not architecture.
  • GitHub issues & PRs remain the place where work is committed to. The pack proposes; it does not promote.
  • Validation receipts remain runtime truth. The pack ends at handoff; proof lives downstream in the runtime-proof surface (Exploration 2).
Floor invariant Design exploration is not architecture authority. Visual guidance is not runtime behavior. Architecture authority remains in repo docs and contracts. Runtime truth remains in shipped code, tests, status docs, and validation receipts. This pack expresses the invariant; it does not loosen it.

What this pack is not

  • Not a new governance pipeline. Mutation continues to flow through the existing policy → validation → event-pipeline → deterministic-writer path.
  • Not a new role or new authority surface. The human reviewer remains the decision-maker; this pack only structures what they see.
  • Not a CI/CD spec. The chain ends at "validation receipt"; how that receipt is produced is owned by runtime-proof, not by design handoff.
  • Not a tool requirement. The console in §04 is a target shape, not a claim that such a console is shipped.

What crosses each boundary

Crossing From → To Required evidence Refusal condition
A Exploration → Handoff package State gallery, edge-case checklist, authority boundaries, open questions, influence table. Missing any required section in the folder shape.
B Handoff → Normalized spec Maturity checklist (§03) passed. Spec written in repo voice (markdown, normative rules, contracts cited). Open questions left unanswered. Conflict with an existing contract not reconciled.
C Spec → GitHub issue Issue references the spec by path. Acceptance criteria copied from the spec. Owner-doc declared. Issue introduces scope the spec does not authorize.
D Issue → PR PR closes a single issue. Tests cover acceptance criteria. Status docs updated. No silent edits to authority docs. PR mutates owner-docs beyond the issue's scope. Tests skip acceptance criteria.
E PR → Validation receipt Runtime proof run. Receipt id recorded in status doc. Skipped checks have stated reasons. Runtime proof skipped without reason. Receipt not linked from the status doc.
Refusal is a feature, not a setback Each boundary is allowed to send the artifact back. A design that fails maturity is not broken — it is correctly held. A PR that mutates owner-docs beyond scope is correctly rejected. The point of the chain is that no single link can promote itself.

03 ·Maturity checklist

A design exploration is mature enough to become a normalized spec when every item on the left is satisfied and no item on the right is open. This is the only gate that decides crossing B.

Ready when all of these are true

  • Scope statement names what is being designed and what is explicitly not.
  • State gallery covers every UI state — at minimum empty, loading, normal, degraded, blocked.
  • Edge-case checklist (§08) is filled, with each item either designed or marked deferred-with-reason.
  • Authority boundaries section names which owner-docs apply and which the design must not touch.
  • Influence table (§09) declares what this design may influence and what it must not decide.
  • Visual guidance is separated from interaction contract is separated from implementation assumptions.
  • Every claim about runtime behavior is sourced or marked target-state.
  • A narrow/mobile layout is at least sketched, even if portrait is deferred.
  • Reduced-motion behavior is described or marked "no motion to reduce".
  • Open questions are written down with proposed owners.

Held when any of these are true

  • An open question would change the state machine if answered.
  • A surface boundary is unclear (which surface owns this action?).
  • An authority boundary conflict with an existing contract is unresolved.
  • A state in the gallery has no described user action set.
  • The design relies on runtime behavior not yet specified in repo docs.
  • The design implicitly introduces a new authority surface.
  • Provenance is shown without saying how it would be produced.
  • Write-guard or denial states are visually absent.
  • Copy treats agent output as semantic authority.
  • No reviewer is named.
Scoring posture The checklist is binary, not weighted. A single hold reason is enough to refuse promotion. That is intentional — promotion is rarer than exploration, and the chain works because the bar at crossing B is high.

The console is intentionally compact. It does not animate. It does not draw the chain on a pannable graph. It does not show contributor avatars. Its only job is to make the chain visible and the maturity bar enforceable at a glance — which is precisely the boundary work the pack is here to do.

Every handoff package opens with a README that the next reviewer reads first. The template below is the minimum shape; fields are deliberately small.

Names the moment in the user's flow this design covers. Names what it deliberately is not. ## Influence May influence: layout, field grouping, copy, visual hierarchy, state coverage May not decide: schema shape, authority flags, mutation paths, runtime contracts Must not loosen: gated-execution invariant, owner-doc authority, write-guard semantics ## Maturity Linked checklist (§03 of the governance pack). Note any deferred-with-reason items. ## Files prototype.html — visual prototype + state gallery design-notes.md — visual guidance, rationale state-gallery.md — every UI state, screenshot or description implementation-contracts.md — fields, intents, testids, classifier expectations authority-boundaries.md — what this design may / may not influence edge-states.md — empty / loading / degraded / blocked / stale / … open-questions.md — unresolved, with proposed owners ## Related Owner-doc citations. Adjacent handoff packages. Any prior version this supersedes. ## Disclaimers Design exploration is not architecture authority. Runtime truth lives in shipped code, tests, status docs, and validation receipts. This package proposes; it does not promote.

06 ·Implementation contract template

The contract document is the part of the package that implementation reads. It is the only document that promises anything to code. Everything else in the package is guidance.

# <Design name> — Implementation contract ## Status Authority: Contract for UI integration · target-state Mutates: nothing on its own Depends on: <runtime contract path>, <runtime contract path> ## State enum The implementation must enumerate exactly these states. Adding a state without amending this document means the design no longer covers it. - <state> description, allowed user actions - <state> … ## Allowed transitions Table of (from, trigger, to). Implementation must reject any other transition. ## Data attributes Stable attributes the design relies on for testids and behavioral selectors. data-testid="<node>" data-intent="<verb.object>" data-<state-axis>="<one-of>" ## Server contract surface Endpoints / events / classifiers the UI consumes. The UI never re-classifies; the server's declared class wins. <endpoint or event> → <ui effect> <classifier> → <ui variant> ## Validation expectations What a passing validation receipt looks like. - render fixture <name> → state <x> - intent <name> emits <event> - denied state shows <reason field> ## What this contract does not say Explicit list of things implementation is free to choose: framework, style technique, animation library, persistence cache shape, network transport.

07 ·Authority & runtime-truth disclaimer template

Every handoff carries this block verbatim — adjust only the lists. It exists so the reader does not need to infer the disclaimer; it is on the page.

# Authority Boundaries & Runtime-Truth Disclaimer ## This design is - Visual guidance for <surface>. - An interaction contract limited to the fields enumerated in implementation-contracts.md. - A target-state proposal until a normalized spec lands in owner-docs. ## This design is not - Architecture authority. Authority lives in: <owner-doc paths>. - Runtime truth. Runtime truth lives in shipped code, tests, status docs, and validation receipts. - A schema. The contract document references fields that the runtime exposes; it does not declare them. - A claim about current runtime behavior unless cited. ## Invariants this design honors - Gated execution. No interaction surface mutates durable state except through the existing governed path: policy, validation, event pipeline, deterministic writer. - Authority separation. Chat is a canvas surface; Panel is the command surface; Automation is its own lane. This design does not collapse them. - Provenance visibility. Where this design shows agent-contributed content, it shows source, trust state, and authority flags. - Bundle integrity. Where this design shows context, it shows what was excluded if exclusion affects interpretation. - Memory candidacy. Where this design shows agent memory, it never treats candidate memory as semantic authority. ## What changes this design may suggest to owner-docs - <path> · <suggested change · why · still subject to owner-doc review> - … ## What changes this design must not suggest - Any loosening of the gated-execution invariant. - Any new authority surface. - Any new write path that bypasses policy / validation. - Any silent promotion of agent memory into semantic knowledge.

08 ·State & edge-case checklist

Every design must answer each of these — design it, or mark it deferred-with-reason. Both are valid. Silence is not.

EMPTY

No content to show. Surface must explain why (no candidates, no context, no history) and what produces content.

LOADING

Awaiting an upstream operation. Surface must be inert (no actions enabled) and distinguishable from empty.

DEGRADED

A subsystem is failing but the surface still functions partially. Must show what is degraded and what is unaffected.

BLOCKED

An action is not allowed. Surface must name the reason in copy, and the denial must be auditable (receipt or session-log turn).

STALE CONTEXT

Context shown is past its expiry. Authority flags drop to the stale-default set; UI shows when it became stale and why.

MISSING PROVENANCE

An item is shown without a source. Must be labelled, must not be promotable, must not be silently authoritative.

WRITE-GUARD DENIAL

A write was attempted and refused. Surface must show denial reason and the receipt id, and must not retry silently.

REDUCED MOTION

All animation must have a static fallback. State changes must be readable without motion cues alone.

NARROW LAYOUT

Designs ship a portrait/mobile sketch or declare portrait deferred-with-reason. Authority labels never collapse to icons alone.

How to mark deferred Add deferred-with-reason: <reason> to the edge-states.md entry. A deferred edge case is a tracked liability, not an oversight; it will be a hold reason if the deferral persists past two packages.

09 ·"May influence / may not decide" table

The single most-skipped section in every prior handoff, and the single most-protective against accidental authority creep. Fill this in for the design at hand. Below is the template shape.

Concern May influence May propose May not decide
UI layout YES — full — —
Copy & microcopy YES — full — —
State machine (UI-side) subset — adds/removes only with owner-doc review YES — propose to owner-doc cannot promote
Field naming on artifacts — YES — propose to owner-doc cannot rename in owner-doc
Authority flags on bundles / memory — propose addition only with rationale cannot loosen existing flags
Endpoints / events — name UI affordances bound to existing endpoints cannot invent endpoints
Classifier outputs — — UI renders what server returns; never re-classifies
Validation receipt shape — may suggest fields the UI needs visible cannot define receipt schema
Persistence shape — — vault / mirror contracts own this
Runtime behavior — — runtime contracts and shipped code only

10 ·Authority & disclaimers

Repeating the floor invariants where they cannot be skipped past.

Invariant · Design is not architecture authority Architecture authority lives in docs/INTERACTION_SURFACES_AND_AUTHORITY/, docs/CONCEPTS/CONTEXT_BUNDLE_CONTRACT.md, docs/CONCEPTS/AGENT_MEMORY_AND_KNOWLEDGE_CONTRACT.md, and adjacent owner-docs. This pack governs the process by which designs become inputs to those docs. It does not become those docs.
Invariant · Runtime truth lives downstream Runtime truth lives in shipped code, tests, status docs, and validation receipts. Nothing in this pack promotes runtime claims. A design may describe an interaction contract; it may not assert that the runtime currently honors it.
Invariant · Gated execution No interaction surface — Panel, Canvas Chat, Automation, or any console proposed in this pack — mutates durable state outside the governed pipeline. Review consoles propose state transitions; they do not write owner-docs.
Process risk · authority creep The single largest risk of a governance pack is the pack itself becoming authority. Mitigation: every section of every handoff cites owner-docs and marks itself target-state. The pack proposes process; owner-docs remain the contract.

11 ·Open questions

  1. Where does the review console live? Is it a tab in the existing AI Panel, a separate page in design_handoff/, or a static HTML rendered from the folder shape? Recommended: static HTML rendered from the folder, no new runtime surface.
  2. Who is the named reviewer at crossing B? The pack assumes a single named reviewer; the team's review topology may want two (visual + contract).
  3. Should "hold" be visible in GitHub? If a package is held at crossing B, should that surface as a label on a draft issue, or stay purely inside the handoff folder?
  4. How are superseded packages handled? Soft delete, archive folder, or status field on the README? Recommended: status field on the README, no folder moves.
  5. Does the validation receipt link back to the package? If so, the package becomes inspectable from the runtime-proof surface — closing the loop. That cross-link is desirable but not a blocker for v1.

12 ·Handoff notes for Claude Code / Codex

What this package would feed if it were normalized.

Likely normalized spec

  • New doc: docs/INTERACTION_SURFACES_AND_AUTHORITY/DESIGN_HANDOFF_GOVERNANCE.md
  • Contents: the flow diagram (§02), the maturity checklist (§03), the influence-table template (§09), the three template skeletons (§05–07).
  • Authority: process pattern. Owner-doc for the handoff process itself. Does not modify any existing contract.

Likely follow-on issues

  • Adopt handoff folder shape across all companion-ui/design_handoff/ entries. Acceptance: every folder contains README, prototype.html, design-notes.md, state-gallery.md, implementation-contracts.md, authority-boundaries.md, edge-states.md, open-questions.md.
  • Add maturity-checklist front-matter to existing handoff READMEs. Acceptance: existing handoffs declare which checklist items they pass.
  • Render the review console statically from the folder. Acceptance: a static page lists packages, their crossing position, and maturity score, with no runtime dependency.

What this design must not feed

  • A runtime review service. The chain is a process pattern; it does not require a server.
  • A new authority over owner-docs. Reviewers and owner-doc owners remain the decision-makers.
  • A blocking gate on PRs. Maturity blocks crossing B (handoff → spec). PRs are gated by the issue's acceptance criteria, not by the handoff package.
Validation expectation If this design is normalized and adopted, a passing receipt is: every package in companion-ui/design_handoff/ conforms to the folder shape, declares maturity, and cites owner-docs. No claim of runtime behavior is made.
