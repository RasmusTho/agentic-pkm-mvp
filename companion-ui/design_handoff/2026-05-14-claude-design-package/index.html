What was designed

Five target-state design packages, each conforming to the folder shape declared by the Handoff Governance Pack (package 1 in this set). Each package contains a visual prototype, a complete state gallery, an implementation contract, an authority-boundaries document, a text-mirror state gallery, an edge-state checklist, and an open-questions log.

What this package is not

  • Not a runtime claim. The Runtime Proof Dashboard renders a snapshot the runtime would emit; it does not assert that snapshot exists today.
  • Not a schema. The Context Bundle Inspector renders the bundle contract; it does not modify it.
  • Not a memory store. The Memory Candidate Review Queue reviews proposals; it does not recall, infer, or promote on its own.
  • Not a control plane. The dashboard mirrors; remediation routes through the existing governed pipeline.

Posture across all four

  • Sober. No alarm dashboards. Red is reserved for actual refusals.
  • Evidence-bearing. Every mono caption corresponds to a runtime value (or names itself as an inferred default that owner-docs would amend).
  • Progressive disclosure. Exclusions, low-trust items, receipt history, and conflict resolution are all one click away rather than always-on.
  • Authority-aware. Authority flags are first-class headers; the UI renders the bundle / candidate / proposal class as declared and never re-classifies.
  • Calm. One animation pattern (receipt pulse + banner LED), respected by prefers-reduced-motion. No emoji. Static stability across states.

Validation expectations

Each package's implementation-contracts.md names the passing-receipt shape. Across all four:

  • Every designed state renders correctly from a fixture.
  • Every declared intent emits the right effect (UI-local / read-only / governed).
  • No UI-derived posture, class, authority, or classification.
  • prefers-reduced-motion respected.
  • Narrow / portrait layout passes the breakpoint acceptance.

05 ·What remains open

Cross-package open questions. Per-package open questions live in each prototype's §09 and the sibling open-questions.md.

  1. Where does the review console actually live? Package 1's review console is target-shape. The recommendation is a static HTML rendered from the folder, not a runtime surface.
  2. Do the four packages need a shared "validation receipt" schema? Each implementation issue produces one. Suggest: a common receipt shape with per-package extension fields. Owner-doc decides.
  3. How does the dashboard's "Run proof" interact with package 1's chain? Should a passing proof on package 2's implementation auto-link back to its package status? Recommended yes; that closes the loop between handoff and runtime truth.
  4. Conditional authority flags. Package 3 (bundle inspector) renders may_propose · conditional; package 4 (memory queue) renders may_recall · maybe. Owner-doc should normalize whether "conditional" is a valid flag state and what it means at each surface.
  5. Cross-links between bundle inspector and memory queue. When a bundle includes a memory candidate, should the inspector deep-link into the queue card? Suggest yes, one-click, no data dependency.
  6. Notification quietness. Packages 2 and 4 both decline to add a badge / counter by default. If the team wants a single quiet indicator anywhere in the shell, owner-doc should decide where (suggest: nowhere; the surfaces are pull).

06 ·How to read this package

For a reviewer at crossing B

  1. Read this index, particularly the Implementation Intake table.
  2. Open each prototype.html and skim §01 (context & boundary) and the state gallery section of each.
  3. Walk the maturity checklist in package 1 §03 against each of packages 2–5.
  4. Triage each open-questions section into block / cite / defer.

For a Claude Code / Codex agent picking up implementation

  1. Read the package's README.md.
  2. Read the package's implementation-contracts.md — this is the only document that promises anything to code.
  3. Open prototype.html, jump to §07 (Implementation contract) and §10 (Handoff notes for Claude Code / Codex).
  4. Use the state gallery (prototype.html §05) and state-gallery.md to enumerate fixtures.

For an owner-doc reviewer

  1. Read the package's authority-boundaries.md — this names exactly what the design may influence in your doc and what it may not decide.
  2. Read the package's open-questions.md — your doc may be the proposed owner for one or more questions.
  3. Read prototype.html §08 (Authority boundaries) for the structured table.
