Vault Action Layer / Agent Tool Authority

Agents do not get raw filesystem powers. They get bounded, governed capabilities, named, classified, gated, and receipted. The vault action layer is the contract between Panel-style instructions ("move this Inbox note to Workbench") and actual mutation. It passes every action through nine steps — intent classification, bounded action, policy, write guard, idempotency, collision-safe execution, receipt, observable event. Obsidian and MCP may later sit as adapters; they may never be the primary mutation path.

Surface: VAULT_ACTION_LAYER Linked issue: #910 Authority: Visual + structural guidance — tool-authority taxonomy proposal Status: Design handoff · v1 · 2026-05-14

01 ·Context & boundary

Why a vault action layer is needed, and what it deliberately is not.

Issue #910 made a broader need visible. Panel Agent — and any future agent — needs bounded vault actions, not raw filesystem or generic Obsidian/MCP powers. Generic write tools collapse the difference between "move a note to a known folder" and "delete an arbitrary file"; they bypass policy, write guard, idempotency, and receipt machinery; they make Obsidian/MCP look canonical when they are properly adapters. The vault action layer is the boundary that fixes this.

What this design covers

  • The 9-step pipeline every vault mutation must pass through.
  • The five-tier tool authority taxonomy agents are bound by.
  • The Obsidian / MCP boundary: adapter, not authority.
  • A concrete first action — "Move current Inbox note to Workbench" — designed end to end.
  • Eight designed states: allowed move, two denial classes, write-guard block, idempotent no-op, collision-resolved, success-with-receipt, receipt-inspection.
Floor invariant · Agents are bounded Agents act through declared vault actions. They do not act through generic write primitives. Every action carries a tier, a policy check, a write-guard verdict, an idempotency check, and a receipt. The runtime owns the action set; the design names the shape that set must take.

What this design is not

  • Not a filesystem API. The pipeline is the contract; the FS calls underneath are the runtime's choice.
  • Not an Obsidian plugin spec or an MCP integration spec. Those may later sit underneath tier-2 bounded write tools as adapters, never as the primary mutation path.
  • Not a UI for arbitrary file management. The vault action layer is for the named actions agents are entitled to. Arbitrary file ops live in the user's own tools.
  • Not a permission model for humans. Humans are the authority; the layer governs what agents may do on the human's behalf.

02 ·9-step action pipeline

Every vault action passes through nine ordered steps. Any step may refuse. Refusal is first-class; it produces a receipt, not silence.

01 · Intent Panel instruction natural-language or structured
02 · Classify Intent → action name router · server-side only
03 · Bound Bounded vault action named, tiered, parameterised
04 · Policy Authority check agent tier · sphere · scope
05 · Guard Write guard policy refusal · focus-mode
06 · Idempotent Idempotency check no-op if already-applied
07 · Execute Collision-safe execution deterministic resolver
08 · Receipt Durable receipt id · action · result · diff
09 · Event Observable event/log outbox + status doc

Invariant · Refusal is first-class Every refusal produces a receipt. There is no silent failure. There is no "tried and nothing happened". A denied action is auditable in exactly the same shape as a successful one — same id format, same trace structure, same status-doc link.

03 ·Tool authority tiers

Five tiers. An agent's maximum tier is set by policy. An action's required tier is fixed by the action registry. Tier mismatch is a policy denial at step 04.

TierNameExamplesWhat it may doReceipt required
Tier 0 Read-only tools read_note, list_inbox, search_vault, get_receipt Read vault state. Return projections. Never mutate. read-trace only
Tier 1 Proposal tools propose_edit, propose_link, propose_move Emit a proposal into the governance queue. Human or governed flow decides whether to apply. Never mutates. proposal-receipt
Tier 2 Bounded write tools move_inbox_note_to_workbench, archive_completed_commitment, append_to_session_log Named, parameter-bounded mutations. Each is a registry entry with declared source domain, destination domain, allowed types, idempotency key shape, collision rule. write-receipt
Tier 3 Governance-bearing tools apply_governance_intent, promote_memory_to_note, change_vault_scope Routes through full governance (Panel review or human accept). Cannot be invoked silently by an agent — always produces a queued intent the human reviews. governance-receipt
Tier 4 Forbidden initially raw_write_file, raw_delete_file, run_shell, eval_javascript Not in the registry. Cannot be invoked. Listed here so the boundary is explicit. Future capability is opt-in per-agent and never default. —

Rules

  • Every action in the registry declares a single tier. Tier is fixed at registration; the runtime does not re-tier at invoke time.
  • Agents declare a maximum invocable tier. Panel Agent's current ceiling is Tier 2 (bounded writes) plus Tier 3 (via human-reviewed governance).
  • Tier 4 is empty. It is named here so it is impossible to "discover" tier 4 by accident.
  • Adding a new bounded write tool (Tier 2) requires a registry entry with the full bounding contract; it is not done at agent runtime.
Tier escalation is not implicit An agent at max-tier 2 cannot invoke a Tier 3 tool by phrasing its request differently. The classifier (step 02) maps intent to action name; the registry (step 03) declares the action's tier; policy (step 04) refuses if the agent's ceiling is below the action's tier. There is no path that loosens this without explicit policy change.

04 ·Obsidian / MCP boundary

Obsidian and MCP are valuable surfaces. They are not the primary mutation authority. Where they appear in the stack, they sit underneath bounded vault actions as adapters, with Yggdrasil's pipeline running first.

What is allowed

  • A Tier 2 bounded action — move_inbox_note_to_workbench — implemented internally by an Obsidian API call. Yggdrasil's pipeline still runs end to end; Obsidian is just the FS-level adapter.
  • An MCP server exposed by Yggdrasil that offers only Tier 0–2 action names from the registry. External callers see actions, not raw write primitives.
  • Read-only Obsidian/MCP tools at Tier 0 — fine as long as they read through the registry.

What is not allowed

  • Generic Obsidian MCP "write file" or "modify note" capability surfaced as an agent tool. That collapses bounding, policy, and write guard.
  • An agent reaching the FS through MCP that does not run Yggdrasil's policy, write guard, idempotency, and receipt steps.
  • An MCP adapter that produces no receipt for a successful or denied action.
  • Treating Obsidian as the source of truth for what an action means. The registry is the source of truth; Obsidian implements.
Invariant · Adapter, not authority Obsidian, MCP, or any future external mutation surface may participate as the execution adapter for a registered Tier-2 action. They may not bypass intent classification, action bounding, policy, write guard, idempotency, or receipt production. The vault action layer runs first; the adapter runs second.

09 ·Authority boundaries

Invariant · Bounded actions, not raw primitives Agents act only through named, tiered, parameter-bounded actions in the registry. Generic write primitives are not exposed. Tier 4 is empty by design.
Invariant · Pipeline is mandatory Every successful action passes all nine steps. Every denied action produces a receipt at the refusing step. No execution adapter — Obsidian, MCP, future — bypasses any step.
Invariant · Receipts are durable Every action — success, denial, no-op, resolution — produces a receipt. The receipt is the audit primitive. Status docs reference the receipt id.

10 ·Open questions

  1. Are Tier 1 (proposal) and Tier 3 (governance-bearing) the same? Both produce a queued artifact for human review. The design separates them because a Tier 1 proposal is the agent saying "I would like to do X", whereas a Tier 3 governance-bearing action is the agent invoking a known action whose semantics require governance (rename, scope change, memory promotion). Owner-doc decides whether the distinction stays.
  2. Idempotency window. 24 hours is a placeholder. Per-action default? Single fixed value? Owner-doc decides.
  3. Collision rule taxonomy. The design names suffix as the first rule. Future rules — merge, refuse, timestamp — should be enumerated in the registry. Suggest: declarative-per-action, never inferred at invoke time.
  4. Cross-vault actions. The first action is single-vault. Multi-vault moves are deferred. Should a Tier 2 multi-vault action be feasible at all, or always Tier 3? Suggest Tier 3 (governance-bearing).
  5. Where do new actions come from? The flow we imagine: a need surfaces (e.g. archive completed commitments), a design exploration proposes the action shape, a normalized spec adds it to the registry. Owner-doc should declare whether registry changes themselves are governance-bearing.
  6. Should classifier confidence affect tier? Currently no — confidence is rendered for transparency but does not gate. If owner-doc wants a low-confidence downgrade, that becomes a step-04 rule.
  7. Receipt retention. How long do action receipts live? Suggest: forever, in vault, as a subordinate artifact. Owner-doc decides.

Likely follow-on issues

  • Register the first bounded action. move_inbox_note_to_workbench@v1. Acceptance: full pipeline runs against a fixture vault; eight designed states render from eight fixture inputs; receipts are durable and inspectable.
  • Define Tier 4 forbidden list. Acceptance: owner-doc names the explicit forbidden primitives (raw write, raw delete, shell, eval) so the boundary is auditable.
  • Define the registry write path. Acceptance: adding a new action requires a PR that lands an entry; the entry declares tier, source/destination domains, allowed types, idempotency key, collision rule, undo strategy.
  • Obsidian adapter for move_inbox_note_to_workbench. Acceptance: action runs through the pipeline; Obsidian performs the FS move; receipt referenced from the status doc.
  • MCP-server exposure boundary. Acceptance: the MCP server exposes only registry actions by name; raw FS primitives are absent.

What this design must not feed

  • A generic "agent tools" library decoupled from the registry.
  • An Obsidian-or-MCP-as-primary-mutation-surface direction.
  • Auto-elevation of an agent's tier at runtime.
  • Silent failure paths.
Validation expectation Passing receipt: the pipeline runs end-to-end against fixture inputs for all eight designed states; refusals produce receipts at the refusing step; the Obsidian adapter path runs the full pipeline; the MCP-exposed surface offers only registry names. Receipt id recorded in this package's status field.
