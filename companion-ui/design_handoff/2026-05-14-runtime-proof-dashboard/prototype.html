Runtime Proof / Health Dashboard

A compact single-operator proof surface. Answers nine questions about whether the local-first runtime is actually working — watcher, worker, outbox, vault scope, write guard, last proof receipt — and points at the next useful action. Not an enterprise observability product, not an alarm panel. Shows evidence, not just color.

Surface: RUNTIME_PROOF_DASHBOARD Audience: the local operator (one human, their vault) Authority: Read-only mirror of runtime state Status: Design handoff · v1 · 2026-05-14

01 ·Context & boundary

What this surface is for, and the postures it must avoid.

Current stabilization work includes watcher OOM repair, worker poison-message handling, startup sequencing, and (later) runtime proof receipts. The dashboard exists to make the outcome of that work legible to the human who runs the vault: not to ops staff, not to a control plane, not to a CI bot. Single operator, one local install, one vault.

Postures we are designing toward

  • Sober. No alarm noise. No red unless red is correct.
  • Evidence-bearing. Every status line is rooted in a value the runtime actually emits (last heartbeat ts, queue depth, receipt id), not a derived colour.
  • Bounded scope. Watcher, worker, outbox/index, vault, write-guard, proof receipt. Nothing else. No latency graphs, no agent traces, no dependency map.
  • Action-aware. When the state suggests a useful next action, the dashboard names it — but does not perform it without explicit trigger.

Postures we are designing against

  • Dashboard-as-control-plane. The dashboard mirrors; it does not orchestrate.
  • Auto-repair. State transitions that look like remediation must be the operator's explicit click.
  • Coloured-tile theatre. A row that flashes amber without saying why is worse than no row at all.
  • "Everything is fine" overcompensation. If the proof has not been run, the surface says that — it does not invent a green check.
Floor invariant The dashboard reads state. It does not write state. Any affordance that looks write-like — "restart watcher", "rebuild index", "run proof" — emits an intent through the existing governed path. The dashboard never auto-triggers remediation.

03 ·Three planes: evidence · status · action

The dashboard renders three planes simultaneously and never lets them blur. Every card, every row, every banner sits cleanly on one plane.

PlaneWhat it isWhere it livesMutability
Evidence Runtime values the system emits — heartbeat ts, queue depth, oldest pending age, restart count, receipt id. Numbers and timestamps. Mono captions inside cards. Per-row values. Sparkline bars. Read-only · never derived in the UI
Status Posture the runtime declares from evidence — running, backlogged, poisoned, stale, denied, pass, fail. Short adjectives or verbs. LED dots. Card headlines. Banner title. Read-only · declared by the snapshot's posture field
Suggested action The single recommendation for what to do next — including "no action needed". Plain second-person language with a verb and an object. Banner sub-line · the bottom next-action strip · per-state gallery cards. Operator-triggered · the dashboard never executes
Invariant · The three planes are never collapsed Evidence does not derive status (the runtime owns posture). Status does not derive action (the suggested-next-action field is its own snapshot field). Action does not execute itself (every action is the operator's explicit click). A coloured tile alone is never a status; a status alone is never an action.

No automatic repair

Every affordance that looks write-like — Run proof now, Restart watcher, Replay dead-lettered event, Rebuild index — is an explicit operator click that emits a governed intent. The dashboard does not retry on its own. The dashboard does not escalate on its own. The dashboard does not flip a subsystem from amber to vault-green by acting; only the runtime does that, and only after the operator triggered the action.

Anti-pattern · auto-remediation If a state appears that wants automatic repair (e.g. "watcher dropped, restart it"), the dashboard surfaces the suggestion in the action plane. The runtime — or, more often, the operator — does the repair. The dashboard is not allowed to become a control plane that hides what it does.

Receipt link pattern

Every status that has a receipt links to it. The pattern is one shape used in three places:

  • Proof receipt panel — the receipt pill is the canonical instance. PASS · rp-2026-05-14-09-14 Click opens the receipt in audit view (read-only).
  • Per-check rows — each check in the proof trace ends with a timestamp that links to the check's own sub-receipt when one exists.
  • Card receipt counts — when a card cites an action count (e.g. 1 pending in Governance, 0 denials · 24h in Write guard), each count is a hover-disclosure that lists the receipt ids; clicking any opens it.
Receipt link rule Any number on the dashboard that represents governed events (proof runs, governance receipts, write-guard denials, dead-letters, watcher restarts) must be a link to the list of receipt ids it counts. Numbers without receipts (heartbeat ms, tick counts) do not link. The pattern makes it impossible to look at a count without being one click from the evidence behind it.

Copy conventions

  • Headline strings are short verbs or adjectives. Never "OK", never "healthy ✓", never emoji.
  • Counts that should be zero render in vault green; counts that should be non-zero render in fg-1 (neutral). Amber and red are reserved for state that wants attention.
  • Timestamps prefer relative ("2.1s ago", "4m") for recent activity and absolute ("09:14") for events that anchor a story.
  • No card shows a percentage. Percentages summarise; this surface does not summarise.
  • The next-action strip uses second-person plain language ("Inspect the poison message", "Run the proof"). Never imperative without an object.

10 ·Open questions

  1. Polling vs push. The snapshot model assumes a poll. If runtime pushes, the polled_at banner field becomes received_at and the refresh button becomes "subscribe / unsubscribe". Either is acceptable to the design.
  2. Single vault scope. The design assumes one active vault per dashboard. Multi-vault would need a vault switcher in the top bar; we have not designed it because the product is single-operator-local.
  3. Proof-run confirmation. "Run proof now" — should it confirm? We suggest no confirmation; proof runs are idempotent and free. Owner-doc decides.
  4. Agent card scope. Should the agent card list every agent (Hugin, Munin, future Deep Agent) or only those with active sessions? Suggest: active sessions and 0-state when none.
  5. What does "blocked" mean in the banner? We use it for policy-blocked writes; we also need a name for "writes denied by failure". Suggest: Running · writes refused for the failure case, Running · focus-mode for the policy case.
  6. How long does the proof history bar span? 14d, 30d, sliding? We suggest 14d as the default; longer ranges live in an inspector linked from the receipt.

11 ·Handoff notes for Claude Code / Codex

Likely normalized spec

  • New doc: docs/RUNTIME_PROOF_DASHBOARD.md — UI guidance only, target-state.
  • References: existing runtime proof receipt contract (when it lands), STATE_EXECUTION_AUTHORITY_REMAINS_GATED.md, panel locality for receipts.

Likely follow-on issues

  • Render the dashboard against a fixture snapshot. Acceptance: dashboard renders nine designed states from nine fixture snapshots without dynamic state.
  • Wire proof.run-now to the proof runner. Acceptance: clicking emits a governed run-request and the receipt id appears in the proof card on completion.
  • Wire outbox.replay-dlq. Acceptance: a per-event confirm dialog appears; replay routes through governance; receipt visible in the governance card.
  • Reduced-motion path. Acceptance: with the OS pref set, no element animates.
  • Narrow layout. Acceptance: 2-col and 1-col layouts preserve card order; the next-action strip becomes a sticky bottom bar.

What this design must not feed

  • Auto-remediation. Every action is the operator's explicit click.
  • An ops-style alert channel. The dashboard does not page; it shows.
  • A definition of healthy. Runtime declares it; UI renders it.
Validation expectation Passing receipt: dashboard renders all nine states from fixture snapshots; intents emit through the governed pipeline; no UI-derived posture; reduced-motion respected; narrow layout passes. Receipt id recorded in this package's status field.
