Memory Candidate Review Queue

A review queue for proposed agent memories. Agents may observe, infer, or summarise — and propose. The queue is where those proposals stop being agent state and start being reviewable candidates. The human can accept, edit, reject, defer, expire, promote, or keep-as-operational. Unreviewed memory is not semantic authority.

Surface: MEMORY_CANDIDATE_REVIEW Owner-doc: AGENT_MEMORY_AND_KNOWLEDGE_CONTRACT Authority: Review surface · review state mutates through governed pipeline Status: Design handoff · v1 · 2026-05-14

01 ·Context & boundary

What this queue is for, and the failure modes it must design against.

The memory contract is intentionally explicit: agent memory supports the human, it does not replace human judgment. Generated or inferred memory may not become trusted knowledge automatically. The candidate → review → promote lifecycle has to be visible, narrow, and bounded. That is the whole reason this queue exists.

It also has to not become a burdensome task inbox. If reviewing memory becomes an obligation, the user will stop reviewing. The design posture is: quiet by default, batched, small, easy to defer, never noisy.

Design posture

  • Single candidate is the unit. A card with content, source, why-now, confidence, authority preview, and seven actions. Everything else is queue chrome.
  • Batch operations require an explicit batch mode. No accidental bulk-accept.
  • Promote is rare and visible. Promotion to durable vault knowledge opens an inline preview of the resulting note before commit.
  • Defer is a first-class action. Deferring is the default-friendly answer to "I don't have time right now" — never a hidden snooze.
  • Operational-only is a first-class outcome. Some memory belongs in agent-side operational memory and should never become vault knowledge. That outcome is a button, not a workaround.
Floor invariant · Candidacy is not authority A candidate in the queue has no semantic authority. The queue's posture defaults prevent candidate-class items from being recalled into answers, orientation, or write proposals. Recall authority is granted only by an explicit accept / promote.

What the queue is not

  • Not a memory store. Storage and recall belong to the runtime; the queue is the review surface.
  • Not an editing surface for already-promoted memory. Revision after promotion flows through the normal vault edit + governance pipeline.
  • Not a task tracker. Memory candidates expire on a schedule; they are not a list of obligations.
  • Not an inbox. There is no notification badge. The queue exists where the user chooses to visit.

Context bundles in the inspector should default to showing their excluded artifacts whenever an exclusion would change how the operator interprets the bundle — for example, when low-trust material was deliberately dropped, or when a closely-related artifact was excluded for being out of scope. 04 ·Queue posture & anti-inbox mitigations

The queue exists to prevent a specific failure mode: agent memory becoming hidden semantic authority. It must do that without becoming a different failure mode: a burdensome task inbox the user starts avoiding.

The persistent authority banner

Every queue view carries the gold banner shown above the candidate list in §03:

In-UI invariant copy Unreviewed memory is not semantic authority. Candidate-state items in this queue cannot be recalled into answers, orientation, or write proposals. Authority activates only on accept or promote.

The banner is mono, gold, and persistent. It never animates. It never collapses. The same banner appears at the top of the batch-mode view and on the single-candidate detail page. It is the surface's floor copy — always present, never opt-out.

Anti-inbox mitigations

Queue anxiety has a known shape: the count climbs, the user feels obliged, the user avoids the surface, the count climbs further. The design refuses each link of that chain.

MitigationWhat it doesWhat it refuses to do
Pull, not push The user visits the queue when they choose. No notification, no badge. No count anywhere in the shell. No “you have N pending” toast.
Defer is first-class “I don’t have time right now” is a button (memory.defer), not a workaround. Re-queues after a chosen interval; no penalty. No “snooze” shame state. No reappearing-twice-as-loud.
Auto-archive expired Candidates past the review window are archived as a stated policy. They are auditable but no longer in the active queue. The queue does not grow without bound. The user is not asked to reject yesterday's noise.
Pacing throttle on inferred If rejection rate is high, the runtime is permitted (per policy) to throttle inferred-candidate proposals per day. (See open question #4.) The queue does not punish a hard day with a louder tomorrow.
Default action by confidence band Low-confidence inferred candidates show defer as the highlighted default — not accept. The frictionless path is the safe one. No accept-first ordering for things the system isn’t sure about.
Batch mode is opt-in Bulk operations exist for cleanup days. They are off by default and require an explicit toggle (queue.toggle-batch). No accidental bulk-accept. Bulk-reject requires a one-line reason that applies to every selected row.
Reject preserves the trail Rejected candidates are auditable, with the reason kept. The trail is the record; the queue is the work. The user is not asked to second-guess past rejections to clean up.
Operational-only is a first-class outcome Some memory belongs in agent-side operational memory and should never become vault knowledge. Keep operational is a button, not a workaround. The user is not forced through accept/reject for things that don’t deserve either.
Promote is rare and visible Promotion opens an inline preview of the resulting vault note before commit. The frequency expectation is set by making this the conspicuous action. The queue is not a fast lane to durable knowledge.
Anti-pattern · “notifications would help” The temptation is to surface a count in the shell so the user remembers to review. That is exactly the failure mode this design refuses. If review becomes obligation, review stops happening, and unreviewed memory accumulates as silent authority — which is the failure mode the queue exists to prevent in the first place.

Healthy posture summary

A healthy queue, by this design's lights, is one where:

  • the user visits the surface on their own schedule,
  • most candidates are deferred, rejected, or operational-only — not accepted,
  • promotion to durable knowledge is rare,
  • the candidate count does not appear anywhere else in the product,
  • and the gold banner stays visible the whole time.

05 ·Action vocabulary

Eight actions. Each names what changes on the candidate, and where the change is recorded.

ActionEffect on candidateEffect on memoryReceipt
Accept state → accepted Becomes recallable as agent memory at the proposed class; authority flags activated candidate_review_receipt
Edit Inline edit on content; state → revised Edited content replaces proposed content; preserves source provenance candidate_revision_receipt
Promote to note state → promoted Creates a vault note (preview shown before commit); memory points at the note promotion_receipt · note path · governance pipeline
Keep operational state → accepted-operational Recallable only as operational memory; never as semantic knowledge candidate_review_receipt
Set expiry Adds expiry to the candidate without changing its review state None — until expiry, candidate stays in queue; on expiry, archived candidate_expiry_receipt
Defer state → deferred; reappears after a chosen interval None candidate_defer_receipt
Reject state → rejected; requires a one-line reason None — candidate stays inspectable for audit, not recall candidate_reject_receipt · reason
Delete state → deleted (rare; for spam/garbage only) None — receipts preserved per memory contract candidate_delete_receipt
Reject > Delete Reject is the default destructive action. Delete is reserved for spam / clearly-bad candidates. The two are distinct because the memory contract requires evidence-trail preservation for rejections; delete is the narrow escape hatch when the candidate should not leave even a rejection trace.

10 ·Open questions

  1. Notification surface. The queue is intentionally pull, not push. Should a small unobtrusive indicator (count badge somewhere quiet) appear when the pending count crosses a threshold? We suggest no badge by default; an opt-in preference is acceptable.
  2. Confidence presentation. Numeric (0.68) vs banded (low / medium / high). We chose numeric because the operator should not infer authority from a band. Owner-doc decides.
  3. Conflict resolution UI. When a candidate conflicts with a prior memory, the design exposes supersede and keep both. Owner-doc should declare whether "keep both" is a permitted memory state.
  4. Pacing. Should the queue throttle inferred candidates per day when rejection rate is high? We suggest yes, as a runtime policy, not a UI feature.
  5. Promotion preview shape. When promoting to a vault note, what is the preview shape — full note with frontmatter, body only, diff against an existing file? Suggest: full preview, with the frontmatter editable.
  6. Auto-archive interval default. 30 days? 14 days? Per-class? The design assumes a default but owner-doc owns the number.
  7. Cross-link to context bundles. If a candidate was inferred from a context bundle, should the why-block link to the bundle inspector? Suggest: yes, one-click.

11 ·Handoff notes for Claude Code / Codex

Likely normalized spec

  • New doc: docs/CONCEPTS/MEMORY_CANDIDATE_REVIEW_UI.md — UI guidance only. References AGENT_MEMORY_AND_KNOWLEDGE_CONTRACT.md.

Likely follow-on issues

  • Render the queue against ten fixture candidates. Acceptance: the ten gallery states render from ten fixture records.
  • Wire seven primary actions. Acceptance: each action emits the right intent, records the right receipt, and updates the queue list.
  • Promote-to-note path. Acceptance: promote opens a preview; confirmation routes through governance; resulting note appears at the declared path; receipt visible in Panel.
  • Conflict UI. Acceptance: supersede / keep-both render only for conflict-state candidates and emit the right intents.
  • Batch mode. Acceptance: bulk-reject requires reason; bulk-accept is disabled without a confidence floor.
  • Reduced-motion + narrow layout. Per §06.

What this design must not feed

  • Auto-accept rules. Every accept is an explicit click.
  • A recall surface. Recall is a runtime property; this queue only governs candidacy.
  • A definition of memory class. Owner-doc owns the classes; the queue renders them.
  • A semantic-search surface across past memories. That is its own design.
Validation expectation Passing receipt: ten state fixtures render correctly; seven primary actions emit the right intents and receipts; conflict UI renders only when conflict is declared; promote-to-note routes through governance; no UI-derived class, confidence, or authority.
