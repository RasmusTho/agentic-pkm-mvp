Context Bundle Inspector

A reviewable surface for the bridge object that sits between retrieval, orientation, resurfacing, and write proposals. Shows what was selected, why it was selected, what was excluded, what authority the bundle carries, and what receipts attach to it. The bundle is the artifact; the inspector exposes it. Semantic similarity is not authority.

Surface: CONTEXT_BUNDLE_INSPECTOR Owner-doc: CONTEXT_BUNDLE_CONTRACT Authority: Visual guidance only — bundle schema not owned here Status: Design handoff · v1 · 2026-05-14

01 ·Context & boundary

What the inspector is for, and what it must never become.

The context bundle contract names a bridge object: an inspectable selection of artifacts, snippets, reasons, exclusions, and authority flags, attached to a single trigger (retrieval, orientation, resurfacing, or action). The inspector is the human's review surface for that object. It exists so the operator can answer "why did the system use these notes before answering, reorienting, resurfacing, or proposing?"

Design posture

  • Inspect, not author. The inspector reads bundles. It does not re-rank, re-classify, or rebuild them.
  • Progressive disclosure. Excluded items, low-trust items, and receipt history are collapsed by default. Their presence is always visible; their contents are one click away.
  • Authority is a first-class header. The five flags (may_answer, may_orient, may_resurface, may_propose, may_write) sit at the top of the bundle, not buried in metadata.
  • Exclusions are visible. If exclusion affects interpretation, the excluded item is shown with its reason. The inspector exposes the negative space.
Floor invariant · Retrieval is not authority A bundle may support an answer without supporting writeback. The inspector renders the bundle's declared authority flags; it never elevates them. If the bundle says may_write: false, the inspector's writeback affordance is absent. Re-classification in the UI is forbidden.

What the inspector is not

  • Not a search UI. Retrieval lives upstream; the inspector explains the result, it does not run new queries.
  • Not a memory surface. Memory candidates have their own queue (Exploration 4). The inspector may reference memory items the bundle includes, never promote them.
  • Not a write surface. Where a bundle has may_write: true, the apply affordance lives in the proposing surface (Panel, Canvas), not here.
  • Not a debugger. The inspector is the human's review surface, not a developer's trace tool.

04 ·Ranked candidates · compact mode · similarity is not authority

Three refinements that make the inspector's contract visually unambiguous: (a) ranked candidates and selected context are not the same picture, (b) provenance has a compact and an expanded view, (c) semantic similarity score is rendered — but score never grants authority.

Ranked candidates → selected context

Retrieval returns a list of candidates. Selection produces the bundle's included + excluded sets. The inspector renders the candidate list as a faded ranked column on the left of the included list — visually subordinate, never the primary surface — so the operator can see what was considered as well as what was chosen.

Selected context (the bundle)

The bundle includes 3 of 8 candidates. Two were excluded for reasons the operator must see (PanelAgent — sphere mismatch; Converse — superseded). Three are below the score floor and rendered only as a collapsed count.

Selection is not a function of score alone — the 0.81 candidate was dropped despite outranking the 0.71 candidate because the 0.81 was out of sphere. The ranking column makes that visible at a glance.

Visual rule Candidates that became included render at full opacity with a coloured role-border. Candidates excluded for a reason that affects interpretation render at 65% with an amber tag. Candidates below the score floor render at 35% with a neutral tag, and may collapse into a single “+N below floor” row.

Compact mode vs expanded provenance

The inspector has two modes. Compact is the default for inline appearance — next to a chat turn, in the AI Panel side-rail, embedded in a write proposal. Expanded is the standalone surface: full ranked column, full aside, full per-artifact provenance.

Semantic similarity is not authority

Invariant Retrieval score answers “how textually similar was this candidate to the query.” It does not answer “may the system use this as a basis to answer, orient, resurface, propose, or write.” Those five permissions are declared by the bundle's authority flags. The score is shown for transparency — so the operator can see selection reasoning — but no UI affordance is gated on score.

Concretely, in this inspector:

  • A 0.93-score artifact in a bundle with may_write: false shows no apply affordance. The score does not unlock writeback.
  • A 0.71-score artifact in a bundle with may_propose: true shows the same propose affordance as a 0.93-score artifact. The score does not rank the affordances either.
  • A bundle with no scores at all (e.g. an orientation bundle) renders the same authority chips as a high-score retrieval bundle. Score is not a precondition.
  • A high-score candidate that was excluded by the selector still appears in the ranked column — score did not buy it inclusion.
Anti-pattern The inspector must never colour a high-score artifact “more green” than a low-score one. Score is rendered in cyan mono as a value, not as a judgment. Authority is rendered as discrete chips. Mixing the two would silently re-introduce the failure mode the bundle contract exists to prevent.

Authority flag rendering rule Every authority flag is rendered explicitly — never inferred. The UI's contract: if the bundle carries five flags, the UI renders five chips. If the bundle adds a sixth (e.g. may_promote for memory), the UI must render it before the bundle is allowed into the inspector — adding silently is forbidden.

09 ·Authority boundaries

Invariant · Semantic similarity is not authority Retrieval scores are shown for transparency, not as a justification for writeback. The inspector never elevates a high-score artifact into a write proposal. Authority flags govern; scores explain.
Invariant · Retrieval output must not authorize writeback Even when may_propose: true, the inspector links to the proposal — it does not apply it. Apply lives in the proposing surface (Panel, Canvas), gated on the governance receipt.
Invariant · Bundles are not memory The inspector may reference memory items the bundle includes. It must not promote those items into memory or knowledge. Promotion routes through the memory candidate queue (Exploration 4).

10 ·Open questions

  1. Default exclusion visibility. The design opens the excluded disclosure when exclusion affects interpretation. The threshold for "affects interpretation" is currently a heuristic. Owner-doc should make it normative — at minimum: low-trust exclusion is always visible; sphere-mismatch is visible by default; mere score-floor exclusion is hidden by default.
  2. Bundle-receipt shape. The inspector lists retrieval / orientation / write-proposal receipts. If a bundle can carry more than these three receipt kinds, the aside list will need a generic shape. We suggest owner-doc declare the receipt taxonomy.
  3. "Why now" on resurfacing bundles. Resurfacing bundles must render a "why now" rationale. Where does that field live in the bundle schema — inside selection_rationale, or as its own resurface_reason?
  4. Cross-bundle navigation. If a write-proposal bundle was produced from a retrieval bundle, should the inspector link between them? We suggest yes, one-click, but the link belongs in receipts not in the body.
  5. Conditional may_propose semantics. We render may_propose: conditional when the bundle's authority is contingent on the proposing surface running its own write-guard. Owner-doc should normalize whether "conditional" is a valid state for any of the five flags, or only for may_propose and may_write.
  6. Memory-class included items. When an included item is an agent memory candidate (not yet promoted), the inspector colours it gold (memory role). Should that always force the bundle's may_write to false? We suggest yes; candidate memory is not semantic authority.

11 ·Handoff notes for Claude Code / Codex

Likely normalized spec

  • New doc: docs/CONCEPTS/CONTEXT_BUNDLE_INSPECTOR_UI.md — UI guidance only. References CONTEXT_BUNDLE_CONTRACT.md for the schema.

Likely follow-on issues

  • Render the inspector against three fixture bundles. Acceptance: retrieval, orientation, write-proposal each render correctly, including authority-chip states and exclusion disclosure default.
  • Render six fail-state fixtures. Stale, empty, blocked, degraded, missing-provenance, write-guard-denied. Acceptance: each renders with the right banner colour, the right downgraded authority chips, and no apply affordance.
  • Narrow / portrait acceptance. All folds work; authority chips never collapse to icons alone.
  • Reduced-motion. Pulses replaced with static colour. State changes still readable.
  • Inspector→Panel handoff. bundle.open-receipt opens Panel anchored to the receipt id; no data dependency.

What this design must not feed

  • A retrieval re-rank surface. Re-ranking is upstream.
  • An apply affordance for write proposals. Apply lives in Panel / Canvas.
  • A memory-promotion surface. Promotion lives in the memory queue.
  • Any change to the bundle schema. The inspector renders; it does not declare.
Validation expectation Passing receipt: nine state fixtures render correctly; authority chips match the bundle verbatim; exclusion disclosure defaults match the threshold rule; narrow layout preserves chip semantics; no UI-derived authority. Receipt id recorded in this package's status field.
