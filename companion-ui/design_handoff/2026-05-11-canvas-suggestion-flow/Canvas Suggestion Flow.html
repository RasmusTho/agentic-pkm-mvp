Companion UI · Design Handoff · Canvas / Hugin

Canvas Suggestion Flow

A narrow, implementation-ready slice covering the moment Hugin proposes a change to the active note, the user previews it, and the system either co-authors the body in place or routes the intent into the governed pipeline. Document is the artifact; chat is the canvas; mutation is gated.

Capability: CANVAS_CHAT_SURFACE Gate: CANVAS_ENABLED Owner-docs: INTERACTION_SURFACES_AND_AUTHORITY Status: Design handoff · v1

01 ·Context interpretation

What this slice is asked to design — and explicitly what it is not.

What is being designed

A document-first co-authoring moment inside the Companion UI rail (or, in portrait, a bottom sheet) anchored to an active vault note. Hugin proposes a change. The user previews it. The user accepts or rejects. The outcome is one of two paths:

  • Body-edit lane. A scoped insertion inside the open note's body during a user-present canvas session. Applied in place by canvas_writer; audited in the subordinate .chats/ session log; reversible by undo.
  • Governance lane. Anything outside the active note's body — frontmatter, tags, maturity, ontology, cross-note links, file moves, multi-note ops. Routed through GovernanceRouter as a queued intent. Returns a receipt; never mutates from chat.

Surface boundaries we are honoring

  • Obsidian / vault remains the canonical durable knowledge surface. The note is the artifact.
  • AI Panel remains the primary command-oriented governance surface. Receipt locality lives there.
  • Companion UI / Canvas Chat is the thinking and co-authoring surface. It is not a second source of truth.
Floor invariant (quoted from STATE_EXECUTION_AUTHORITY_REMAINS_GATED) No interaction surface mutates durable state except through the existing governed path: policy, validation, event pipeline, and the deterministic note writer. LLM reasoning alone never triggers execution. This slice expresses the invariant; it does not loosen it.

What this slice is not

  • Not a redesign of the Companion UI shell. The converse layout, session drawer, and rail collapse states stay as shipped.
  • Not a dashboard, not a chat-as-primary-artifact, not a separate semantic store.
  • Not a new governance pipeline. Governance-bearing intents enter the existing pipeline as a queued request.
  • Not a runtime spec for the writer, router, or session log — those are already specified in CANVAS_CHAT_SURFACE/.

03 ·UI state model

Eight states. Two orthogonal axes: session activity (idle / thinking) and proposal lifecycle (staged / pending / resolved / blocked).

State enum

The composer is enabled in idle only. In every other state the input is read-only with state-appropriate placeholder copy (e.g. "Hugin is thinking…", "Apply or discard to continue", "Queue or discard to continue", "Canvas disabled in this environment").

Server is the classifier Whether a proposal is body-class or governance-class is set by the server on the proposal payload — derived by GovernanceRouter classification. 07 ·Body-edit lane

User-present, in-place co-authoring of the open note's body. Authorized by presence. Audited by session log. Reversible by undo.

Preview semantics

  • The proposed text is shown inline at the insertion point in the document pane (orange marker, "PROPOSED · UNCOMMITTED" label) and as a mirrored card in the rail thread.
  • Both visualizations share a data-suggestion-id so DOM events on one can drive highlight states on the other.
  • The user may Inspect diff (expands the rail card) or Edit before applying (inline edit on the proposed text in the rail). Edits do not mutate the note until Apply.

Apply semantics

  • Single round-trip: UI calls canvas_writer.apply_edit(session_id, edit). On success, the in-document marker flips to vault green with the applied receipt id; the rail card collapses to a one-line "applied" log entry.
  • The session log gains a turn entry: kind: body_edit_applied, note_path, anchor, byte_range, preview_hash.
  • Apply is not a governance event; no receipt is queued in the Panel pipeline.

Discard semantics

  • Local-only. The preview is removed from the document pane and the rail card is rendered struck-through and dimmed.
  • A turn entry kind: body_edit_discarded is appended to the session log so provenance still captures the proposed-but-rejected suggestion.

Undo semantics

  • The provenance footer exposes data-intent="canvas.undoLastEdit". Undo inverts the last applied body edit by calling canvas_writer.apply_edit with the inverse patch; the session log records kind: body_edit_undone.
  • Undo is bounded to the active session. Cross-session undo is out of scope and explicitly deferred to a later capability.

08 ·Governance-bearing lane

Anything outside the active note's body. Cannot be applied from chat. Must enter the governed pipeline as a queued intent.

What qualifies as governance-bearing (UI surface copy)

  • Frontmatter changes (tags, maturity, type, ontology).
  • Note lifecycle (rename, move, archive, delete, promote).
  • Cross-note operations (link, merge, split, create-and-link).
  • System-owned artifacts (automations, watchers, scheduled jobs, agent instructions).
  • Edits to notes other than the active one.
Hard UI rule The governance variant has no Apply button. The primary action is Queue for governance. The card carries a visible classification label — "Cannot be applied from chat — must be queued" — anchored to a help target that opens the Panel governance docs.

Queue semantics

  • UI calls GovernanceRouter.request_governance_action(action_type, payload, session_id).
  • On success: the router returns a receipt id; the rail renders a queued <ReceiptPill> inline, and adds it to <ReceiptsStrip> at the bottom of the rail. Session log gains kind: governance_intent_queued with the receipt id and action type.
  • On write-guard denial (e.g. CANVAS_ENABLED=0, policy refusal): the card transitions to blocked; the session log gains kind: governance_intent_blocked with a reason field.

Status after queue

  • The pending receipt remains visible in the rail's receipts strip until status changes upstream.
  • Status transitions (queued → in-review → applied or rejected) are read-only in the canvas — the user inspects and acts on them in AI Panel. data-intent="governance.openReceipt" hands off to Panel.
  • The Companion UI never auto-applies or auto-rejects a governance receipt.

09 ·Receipts & provenance behavior

Two distinct artifacts: in-pipeline receipts (Panel locality) and the per-session session log (subordinate vault artifact).

Receipts

  • Lifecycle: queued → in-review → applied | rejected.
  • Locality: Panel's receipt store, unchanged. Companion UI mirrors but never owns.
  • Rendered as a <ReceiptPill> inline in the thread at the moment of queue, and as a row in <ReceiptsStrip> for as long as the receipt is non-terminal.
  • Body-edit applies do not generate a receipt. They are not governance events.

Session log

  • Path: vault/.chats/<note-slug>/<timestamp>.md (per WRITE_SESSION_LOGS).
  • Frontmatter: type: chat-session, note_path, opened_at, closed_at.
  • Append-only. Turns are appended via SessionLogWriter.append_turn. The UI never rewrites prior content.
  • Subordinate, not canonical. The active note remains the artifact. The session log is provenance.

10 ·Responsive behavior

Two layouts, one state model. The rail collapses to a bottom sheet at portrait widths; the suggestion-card lives in whichever container is mounted.

Landscape (≥ 900 px wide)

  • Two columns. Document pane primary; rail on the right (collapsed strip / expanded).
  • <SuggestedInsertion> renders inline in the document pane.
  • <SuggestionCard> renders in the rail thread.
  • <ReceiptsStrip> sticks to the bottom of the rail, above the composer.

Portrait / narrow (< 900 px wide)

  • Document pane fills viewport; rail replaced by <BottomSheet> with three snap points: peek (60 px, shows hugin dot + turn count), half (50vh), full (calc(100vh - 64px)).
  • When a proposal arrives the sheet auto-snaps from peek → half; never to full (so the document is still visible at the insertion point).
  • <SuggestedInsertion> in the document pane is the user's primary read of the change; the sheet card is the action surface.
  • <ReceiptsStrip> renders at the top of the sheet (sticky) so pending governance items remain visible when the user scrolls the thread.

Cross-cutting

  • Hit targets ≥ 44 px in portrait. Apply and Queue are always the primary (color-distinct) action; Discard is always secondary.
  • Sheet snap state is persisted to localStorage per session id so refresh keeps context.
  • Reduced-motion users skip the thinking pulse and the sheet auto-snap; the proposal still arrives, just statically.

11 ·Accessibility requirements

Keyboard

  • Composer focused by default in idle. Esc from the composer collapses the rail (landscape) or snaps the sheet to peek (portrait).
  • On suggestion-staged, focus moves to the primary action of the suggestion card (Apply or Queue). A applies (body lane only); Q queues (governance lane only); D discards; I inspects; E edits-before-applying (body only). Composer is removed from the tab order while staged.
  • The receipts strip is reachable from the rail header with a single tab; pills expose aria-label with action type and receipt status.

Live regions

  • <ConversationThread> has aria-live="polite" with relevant updates announcing only new messages and proposals (suppress the thinking pulse).
  • <ReceiptsStrip> has aria-live="polite" on its row list so status transitions from upstream are announced even when focus is on the document.

Labels & semantics

  • <SuggestedInsertion> is a <ins> in the DOM with a data-state attribute and an aria-label announcing "Proposed insertion, <n> lines after <anchor>".
  • <SuggestionCard variant="governance"> has aria-describedby pointing at the classification label so screen readers always announce the "must be queued" constraint.
  • <SuggestionCard variant="blocked"> has role="alert" and an aria-describedby for the denial reason.

Contrast & reduced motion

  • All state colors (amber staged, vault applied, accent governance, destructive blocked) meet ≥ 4.5:1 against the surface they sit on. The Yggdrasil tokens already satisfy this.
  • @media (prefers-reduced-motion) disables the thinking dot pulse and the receipt-pill pulse; transitions resolve to instantaneous.

14 ·Open questions & risks

Open questions

  1. Multi-suggestion threading. If a turn returns more than one proposal, does the UI batch them into one card or stack independent cards? Defaulting to stacked, one-at-a-time apply; needs confirmation.
  2. Receipt status freshness. Polling vs push from Panel for governance receipt status. Polling is fine for the v1 slice; push is deferred.
  3. Inline edit-before-apply provenance. If the user edits the proposed text before applying, is the original proposal still logged, the final text logged, or both? Recommended: both (with proposal_hash and applied_hash).
  4. Undo scope. Confirmed bounded to the active session. Cross-session undo is explicitly deferred — needs a follow-up capability.
  5. Sheet behavior on incoming proposal mid-composer-typing. Auto-snap risks stealing focus. Recommendation: surface a non-stealing indicator in the peek strip and let the user choose to expand. Needs UX validation.
  6. Concurrent edits. If the active note is edited in Obsidian during a canvas session, what happens to staged suggestions whose anchors moved? Recommendation: invalidate and re-stage from server; needs confirmation with canvas_writer semantics.

Risks

  1. Surface drift. If the UI ever offers an Apply button on a governance proposal — even as a "shortcut" — the gated-execution invariant breaks. Lint the component: governance variant must never render an apply intent.
  2. Session-log inflation. Discarded proposals are appended to provenance. Verbose sessions could bloat .chats/. Mitigation: append_turn writes summaries, not full proposal bodies, when the proposal was rejected.
  3. Receipt orphaning. A receipt queued from canvas whose Panel record is dismissed elsewhere leaves a stale pill in the rail. Mitigation: receipts strip reads from Panel locality, not from a canvas-local cache.
  4. Classification drift. If the server's classifier and the UI's lane rendering diverge in vocabulary, blocked-card reasons become unparseable. Mitigation: share a single enum GovernanceActionType across both sides.
