Yggdrasil · Companion UI · User Guide

A calm shell for thinking with your notes.

Companion UI is a local-first browser interface that puts your active note at the centre. It gives you access to an AI that can co-author the note body, surface agent proposals for review, and help you re-enter context after time away — without ever writing to the vault except through an auditable, receipt-bearing execution path.

01What is Companion UI

A cognitive prosthesis, not a productivity dashboard.

Companion UI is a browser-accessible workspace served by the Yggdrasil host process. It does not replace Obsidian. Your vault remains the canonical home for every durable knowledge artifact. Companion UI augments how you interact with that vault — adding agent-assisted editing, governed proposal review, and session continuity — while keeping the document itself the undisputed cognitive anchor.

Three principles govern every surface in the UI:

  • Document-first. The active note is always the primary visual element. Everything else is subordinate chrome.
  • Overlay-first. Agent contributions appear as reviewable overlays, not as hard navigation or page-replacing views.
  • Human decides. The AI surfaces intent and suggestions; the human confirms, corrects, or rejects before anything is written.
Design principle

Hidden semantic state is prohibited. Every status the system holds — write-guard status, canvas enabled/disabled, session recovery state, proposal classification — must be visible in the UI when relevant. The system must not look "fine" while hiding a blocked or degraded condition.

03Reading a note

The note opens through the runtime — the UI never reads the vault directly.

When you navigate to a note, the runtime resolves the active artifact and returns its identity, path, content hash, and capability flags. The UI renders what the runtime declares; it never selects or reads vault files itself.

Artifact identity strip

Below the note title you will see a thin identity strip containing:

  • Note path — the vault-relative path (Projects/Q2-arch.md).
  • Content hash — a short hash of the current note body, used for conflict detection and Canvas edit guards.
  • Session reference — the current Canvas session ID, if a session is active.
  • Environment label — the runtime environment (local-dev, staging, etc.).

WriteGuard and Canvas status

The top of the companion rail shows a compact status strip. Two flags are always visible:

  • WriteGuard — whether the runtime allows vault writes. If write-guard is blocked, Canvas editing and Panel confirmations are disabled until the guard clears.
  • Canvas — whether the Canvas edit surface is enabled for this environment. Disabled when CANVAS_ENABLED=0 on the server.
Degraded state

If the runtime is unreachable, or if the workspace payload cannot be loaded, the UI shows a full-width alert. It does not silently fall through to a blank or stale note view. The status strip turns amber and describes the condition.

04Canvas — body editing

Direct in-place note-body co-authoring, undo-capable and receipt-bearing.

Canvas is the co-authoring surface for the active note body. It is separate from the Panel (which handles governed proposals) and from the Converse/Chat surface (which is a canvas-like conversational input). Canvas edits go directly to the note body through the runtime writer; each edit is logged in the session provenance trail.

Starting a Canvas session

A Canvas session opens automatically when you first submit a body-edit intent in the Converse input, or when the server stages a body-edit suggestion for review. The session is identified by a short ID shown in the identity strip and in the companion rail header.

Session scope

Each Canvas session is bound to the note that was active when the session opened. Navigating to a different note closes the current session and opens a new one.

Applying and undoing edits

1
Propose
Type your editing intent in the Converse input. The agent processes the request and stages a preview of the proposed change.
2
Preview
The staged suggestion appears in the companion rail with a diff or preview of the proposed body change.
3
Apply
Press A or click Apply. The runtime writes the change via the CanvasWriter. The note body updates in the document pane.
4
Undo (if needed)
After applying, an Undo option remains available in the companion rail. Pressing it sends the prior body to the CanvasWriter, restoring the note to its pre-edit state. Undo is available only for the most recent edit.
5
Session log
Every applied edit is recorded in a session log. The ProvenanceFooter in the companion rail shows the log path. This is an intent trail, not the artifact — the note is the artifact.

Session recovery

If a Canvas session is interrupted — browser closed, network drop, hash mismatch — the next time the same note opens the UI detects the conflict and shows a recovery card in the companion rail. You must acknowledge the recovery state before Canvas editing can resume. The acknowledgement is a UI-local action; it does not write to the vault.

05Canvas suggestion flow

Two kinds of suggestion: body edits and governance proposals.

When the agent produces a suggestion it is always pre-classified by the server before the UI renders it. The UI never reclassifies a suggestion. Classification determines which actions are available to you.

Classification What it means Actions available
body A proposed change to the note body text. No governance side-effects; can be applied directly via the CanvasWriter. Apply (A), Discard (D), Inspect (I), Dismiss rail (E)
governance A proposal that touches governed artifact state — lifecycle moves, tag changes, cross-note operations. Must travel through the Panel pipeline before execution. Queue (Q), Discard (D), Inspect (I), Dismiss rail (E)
blocked Canvas is disabled on the server (CANVAS_ENABLED=0) or WriteGuard is blocking writes. No mutation actions available. Inspect (I), Dismiss rail (E)
Hard invariant

A governance-classified suggestion never has an Apply button. Applying a body edit never creates a Panel governance receipt. The two pipelines do not cross.

Rail states

idle
No active suggestion. Converse composer is enabled and has keyboard focus.
thinking
Agent is processing a request. Composer is disabled. A spinner indicates progress.
staged body / staged governance
A suggestion is awaiting your decision. Keyboard shortcuts are active. Composer is disabled until you act.
apply pending / governance pending
A write or governance queue call is in flight. UI is locked; do not navigate away.
applied / discarded
Terminal presentation state. Outcome is shown with a receipt pill. Rail returns to idle after acknowledgement.
blocked
Canvas is unavailable. Mutation actions are removed. The block reason is displayed.
06Panel — proposals

Artifact-local intent. You recognize and confirm; the runtime executes.

Panel is the governed proposal surface for the active artifact. It is separate from Canvas (which edits the note body) and separate from any global inbox view (Companion UI does not have one). Panel proposals are bounded to the note currently open.

The agent may surface what it believes you likely want to do with this specific artifact — a lifecycle move, a tagging decision, a follow-up action — before you have explicitly commanded it. You review the proposal, read the evidence, and decide to confirm, correct, or reject.

Reading a Panel proposal

Each proposal row in the companion rail shows:

  • Proposal label — what the agent is proposing in plain language.
  • Evidence — the source references or reasoning the agent used, shown as collapsed evidence links you can expand.
  • Trust state — whether the proposal came from a reviewed agent path or is provisional.
  • Authority flags — the governance class of the proposed action (e.g., lifecycle move, classification, cross-note).

Confirming a proposal

1
Review
Read the proposal and the evidence. Expand evidence links if you need to trace the reasoning back to source material.
2
Correct or confirm
You can edit the proposal text before confirming. The corrected intent replaces the original. Your correction is part of the receipt.
3
Confirm
Clicking Confirm routes the intent into the governed execution path: policy check → WriteGuard → idempotency guard → deterministic writer → receipt.
4
Receipt
A receipt pill appears showing the outcome (confirmed, blocked, or error). Receipts persist in the companion rail for the duration of the session. The outcome is never hidden after the action completes.
No silent execution

Panel never auto-executes a proposal. LLM output from Panel cognition is always in the proposal or clarification class; it is never promoted to governed-execution authority without explicit human confirmation.

07Reorient

Re-enter your context after time away — read-only, advisory, no execution.

The Reorient card appears in the companion rail when you open a note you have not visited recently, or when a session has been interrupted. It summarises where work left off using bounded evidence from the session log and vault history.

What Reorient shows

  • A short plain-language summary of the last meaningful activity on this note.
  • Evidence links to the session log turns or vault artifacts that ground the summary.
  • Any open Canvas or Panel state from the prior session, if recovery is needed.
Advisory only

Reorient never executes actions on your behalf. It is a read-side recovery surface. Nothing in the Reorient card has write authority. If you see a suggestion that looks like a proposal, it will route through Canvas or Panel, not execute directly from the Reorient card.

Dismissing Reorient

You can dismiss the Reorient card at any time by clicking the dismiss control in its header. The card does not reappear during the same session unless a new recovery condition is detected.

08Resurface & Find

Low-pressure candidates and search — both bounded by what the runtime can provide.

Resurface

Resurface shows read-only memory candidates and related note fragments that may be relevant to the active artifact. It is intentionally low-pressure: the UI must not imply urgency unless the runtime explicitly signals urgency in its payload.

Resurface candidates are presented as expandable pills in the companion rail. They do not carry Apply buttons. If a candidate looks useful, you can copy a reference into the Converse input and ask the agent to act on it — that action then travels through the normal Canvas or Panel flow.

Memory is not semantic authority

Unreviewed memory candidates shown in the Resurface rail are provisional. They are not promoted to semantic authority until you explicitly confirm or promote them through the governed path. The UI labels each candidate with its provenance and review status.

Find

Find is a note-search surface available from the top bar. In the current MLP it may show a candidate or unavailable state if the backend search index is not ready. The UI will say so explicitly rather than returning empty results.

  • Find results link to notes, not inline-insert text.
  • Opening a result replaces the active note in the document pane.
  • Find does not support full retrieval of all vault content; it queries the index the runtime exposes.
09Keyboard shortcuts

Shortcuts are active only when a suggestion is staged and awaiting your action.

Global keyboard shortcuts are minimal. Context-scoped shortcuts activate when the companion rail has a staged suggestion — the shortcuts are shown in the suggestion card so you do not need to memorise them.

Suggestion rail shortcuts

These shortcuts are active only when data-suggestion-state is staged-body or staged-gov, and only when no text input is focused elsewhere.

Key Action Available when
A Apply body suggestion — writes the staged body edit via the CanvasWriter. Body suggestion staged · Canvas enabled · not blocked
Q Queue governance suggestion — routes the staged governance intent through the GovernanceRouter; returns a receipt pill. Governance suggestion staged · not blocked
D Discard suggestion — removes the staged suggestion without any write. Composer returns to focus. Any staged state · not blocked · not terminal
I Inspect — expands the suggestion card to show full diff, provenance, and evidence. No mutation. Any staged state · blocked · terminal
E Dismiss rail / edit — collapses the suggestion card and returns composer focus so you can refine your request. Any staged state · blocked · terminal
Tip

In blocked and terminal (applied/discarded) states only I and E are active. Apply and Queue are removed to prevent accidental mutation when the path is not open.

10UI state signals

What the UI shows when things are not normal.

Companion UI is designed to speak its null and degraded states explicitly. Below is a reference for the signals you may encounter.

Signal What it means Action needed
WRITEGUARD · BLOCKED The runtime write guard is active. Canvas edits and Panel confirmations cannot proceed. Check runtime health. The guard clears server-side when the blocking condition resolves.
CANVAS disabled CANVAS_ENABLED=0 is set on the server. The Canvas edit surface is not available in this environment. Use the environment where Canvas is enabled, or wait for a server flag change.
Session recovery needed A Canvas session was interrupted — hash mismatch, browser close, or network drop. The current note body may differ from session state. Read the recovery card and acknowledge it. Canvas editing resumes after acknowledgement.
Identity unresolved The runtime could not confirm artifact identity for the active note. The note path or ID is provisional. The UI shows the unresolved state in the identity strip. Do not apply edits while identity is unresolved.
Find unavailable The search index is not ready or the runtime does not expose a search endpoint for the current environment. The UI labels this state rather than showing empty results. No action needed unless search is required.
Runtime unreachable The Yggdrasil host process cannot be reached. The UI cannot load the workspace payload. Check that the host process is running (make alpha-up or equivalent). Refresh when service is restored.
No active Panel proposal The Panel rail is idle — the agent has not surfaced a proposal for the current artifact. Normal idle state. No action needed.
11Authority boundaries

What the UI can and cannot do — by design, not by limitation.

These boundaries are intentional. They preserve the governance invariants that make the system trustworthy. They apply unconditionally; no feature request or configuration change can override them without an explicit owner-doc change.

The UI cannot and will not

  • Read vault files directly. All content comes through the runtime API.
  • Write vault files directly. All writes route through the governed execution path: policy → WriteGuard → idempotency → deterministic writer → receipt.
  • Choose or configure which vault is active. Vault binding is a runtime decision. The UI renders what the runtime declares.
  • Reclassify server-declared proposals. If the server says a suggestion is governance, the UI renders it as governance. The UI never upgrades or downgrades proposal class.
  • Execute Panel proposals without your confirmation. LLM output is always in the proposal class; you confirm before anything enters the execution path.
  • Persist runtime state to the vault silently. Session logs are provenance trails. Durable vault writes are receipt-bearing and visible.
  • Operate as a second Obsidian. The vault is canonical. Companion UI is a client surface for that vault.

The UI is explicitly authorised to

  • Render the active note body from the runtime-provided payload.
  • Display runtime-declared state: WriteGuard status, Canvas enabled flag, session recovery state, artifact identity, content hash.
  • Co-author the note body via the Canvas session flow, with your apply confirmation at every step.
  • Surface agent proposals in the Panel rail and route your confirmation into the governed pipeline.
  • Show read-only session provenance, Reorient summaries, and Resurface candidates.
  • Display receipts for all completed actions, including block reasons.
Authority hierarchy

Runtime declares class, posture, and authority. The UI renders what the server declares. The UI never re-declares. If a runtime response and a UI element appear to conflict, the runtime response is authoritative.
