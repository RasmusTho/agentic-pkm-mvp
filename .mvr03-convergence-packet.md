# MVR-03 mechanism convergence packet

SHA under review: local publishable head on `codex/issue-3857-active-context-selection`.
Declared risk surfaces: auth, security, data, migration, concurrency, credential-durability,
state-machine.

Three distinct stateful mechanisms ship here. They are documented separately because they fail
independently.

---

## Mechanism A — delegated local-operator principal record (durable)

**State**: one private JSON file, `<instance-state>/agentic-pkm/local-operator-principal.json`,
mode `0600` inside a mode-`0700` directory. Schema `agentic-pkm.local-operator-principal.v1`.
Fields: `revision` (monotonic), `local_operator_role_id` (CSPRNG, opaque),
`subjects` (subset of `trusted_loopback` / `trusted_companion_proxy` / `api_key_credential`),
`credential_fingerprint` (sha256, domain-separated; never the raw key), `migration_provenance`,
`created_at` / `updated_at`, `additional_roles`.

**Invariants**

1. The role id is never derived from the credential, its fingerprint, `appInstallId`, or a path.
2. The raw credential never reaches durable state, a log, a receipt, or a cache key.
3. Rotation preserves `local_operator_role_id` and never drops the loopback/proxy subjects.
4. An explicitly added human/agent role gets a **distinct** principal id.
5. A governed operation with no resolved principal fails closed. There is no anonymous branch.
6. The first durable write cannot precede the `minimum_runtime_principal` floor.

**Transitions**

| from | event | to | writer |
| --- | --- | --- | --- |
| absent | `bootstrap` (floor recorded) | rev 1 | `LocalOperatorPrincipalStore.bootstrap` |
| absent | `bootstrap` (no floor) | absent | refused — `PrincipalFloorNotRecordedError` |
| rev N | `bootstrap` same posture | rev N | idempotent no-op |
| rev N | `bootstrap` different posture | rev N | refused — use rotate/add-subject |
| rev N | `rotate_credential` | rev N+1, same role id | `rotate_credential` |
| rev N | `revoke_subject` (>1 subject) | rev N+1 | `revoke_subject` |
| rev N | `revoke_subject` (last subject) | rev N | refused |
| rev N | `reconcile_roll_forward` (unambiguous rotation) | rev N+1, same role id | `reconcile_roll_forward` |
| rev N | roll-forward missing / divergent fork / ambiguous | rev N | refused, neither lineage overwritten |

**Locks and crash ordering.** Every mutator runs under `flock(LOCK_EX)` on a `0600` `.lock`
sidecar, then `mkstemp` → `fchmod 0600` → `write` → `fsync(file)` → `os.replace` → `chmod 0600`
→ `fsync(parent dir)`. A crash at any point before `os.replace` leaves the prior record intact
and the temp file orphaned but unreferenced (unlinked in the `except` path). There is no
read-modify-write across the lock boundary: each mutator loads inside the lock it will write
under.

**Read-side safety.** `_read_private_json` refuses a non-regular file, wrong owner, or non-`0600`
mode before parsing. A partial record raises rather than reading as "no principal yet" — that
distinction matters, because returning `None` would re-run bootstrap over live state.

**Producers / consumers / recovery.**
- Producers, all shipped CLI commands on `python -m app.instance.runtime`:
  `principal-record-floor`, `principal-bootstrap`, `principal-rotate-credential`,
  `principal-add-role`, `principal-revoke-subject`, `principal-export-auth-state`,
  `principal-roll-forward`. The first two are invoked by
  `scripts/lib/instance_state_deployment.sh` under `MVR03_PRINCIPAL_CUTOVER=1`; the test
  harness drives that same command rather than the writer, so a producerless invariant fails
  the ops test rather than passing silently.
- Transitions additionally include `add_role` (rev N -> N+1, distinct principal id) and
  `revoke_subject`.
- `reconcile_roll_forward` **consumes** the export on success (and on the no-op branch), and
  the fork check is `!=`, so a stale export cannot replay over a later governed rotation.
- `principal-export-auth-state` exports the prior image's *configured* credential read from
  its environment, not the role record's own fingerprint.
- Consumers: `app/api/routes/active_context_selection.py` (via `open_local_operator_principal_store`)
  and `python -m app.instance.runtime principal-show`.
- Recovery: none is silent. Every failure raises `PrincipalPreflightError` carrying an explicit
  `provisioning_action`.

## Mechanism B — `minimum_runtime_principal` floor + auth-producer fence (durable)

**State**: `RegistrySnapshot.extensions["runtimeFloors"]["minimumRuntimePrincipal"] = "mvr-03"`,
plus `extensions["principalState"]["fence"]` recording the inventory that authorized it.

**Deliberate reuse**: this is MVR-01's existing `runtimeFloors` slot and its existing
`set_extension_state` writer, not a second floor mechanism. `record_principal_floor` reads the
current `dimensions` / `principalState` / `backgroundState` back and re-supplies them unchanged,
because `set_extension_state` writes all four slots together and a partial write would erase a
sibling.

**Ordering (enforced, fail-closed at each step).** MVR-03 runs *inside MVR-01B's existing
stopped window* rather than opening its own. This is the mechanism-level convergence answer to
the round-1 P0 and round-2 NEW-1/NEW-2: MVR-03's auth producers are the same processes MVR-01B
already inventories, drains, stops, proves quiescent from production truth, and restart-fences,
so a second drain/probe/inventory producer would be a duplicate mechanism -- and, unwired, a
mechanism with no production producer at all.

SCOPE BOUNDARY, stated plainly: the wrapper does NOT invoke steps 3-4. Three review rounds
found blockers in that link (posture and native launcher paths are unavailable inside the
`instance-state-init` one-shot), and the repair budget for the mechanism is spent. Shipping it
half-wired is worse than not shipping it, because a cutover that records the floor and then
fails the role write leaves the instance fenced and rollback-blocked. The floor now preflights
the bootstrap posture *before* recording, so that ordering is unreachable in code; the operator
runs steps 3-4 explicitly inside the window. Automated activation is bounded follow-up work.

    scripts/lib/instance_state_deployment.sh:
      deployment-begin (durable restart fence)
        -> compose stop api worker watcher heimdal-capture-watch
        -> instance_state_writer_inventory.py prove-quiescent (2 identical probes)
        -> deployment-prove (binds proof to the channel lease)
        -> [operator] principal-record-floor
                                    <-- requires the proved lease for this channel+nonce
                                        (schema, phase, all_consumers_stopped, inventory
                                        digest, controller), preflights the bootstrap
                                        posture,
                                        consumes that proof + the drained legacy-owner
                                        inventory, enumerates compose (fails closed on an
                                        unclassified service), adds the producers MVR-01B
                                        does not classify, then records the floor
        -> [operator] principal-bootstrap  <-- refuses while the floor is absent
        -> deployment-finish

**`require_complete_fence` rejects**: wrong schema, operations not fenced, `probe_count < 2`,
any missing producer *role*, any enabled producer not (`stopped` ∧ `restart_fenced` ∧
`write_handle_released`).

**Crash ordering.** A crash before the floor write leaves old auth state authoritative and the
migration untouched (`record_principal_floor` performs no write until `require_complete_fence`
returns). A crash after the floor but before the role write leaves the floor recorded and the
record absent; the next bootstrap sees `floor_recorded=True` and completes. A crash after the
role write is the terminal state.

**Rollback interaction.** `_require_runtime_floor(..., scalar_runtime=True)` raises
`CapabilityNotReadyError` while the floor exists. It is called from
`_preflight_scalar_rollback_locked` *before* `materialize_legacy_rollback`, so a refused rollback
materializes no legacy projection.

**Inventory derivation.** `discover_auth_producers` **enumerates** the real
`docker-compose.yaml` and requires every service to be classified either auth-bearing
(`COMPOSE_AUTH_SERVICES`) or explicitly reviewed non-auth (`COMPOSE_NON_AUTH_SERVICES`); an
unclassified service raises. Checking a hand-written list *against* compose was the earlier
design and was rejected: it detects a renamed service but silently misses an **added** one,
which is exactly how a new auth producer would escape the fence. Source paths are explicit
mounted arguments (`--compose-base`, `--native-producer-root`), never derived from `__file__`,
because the runtime image carries no repo checkout.

## Mechanism C — TTL-bound session selection + generation rotation (ephemeral, concurrent)

**State**: one in-process `dict[raw_selection_id, ContextSelectionRecord]`, plus a per-resolver
`{(context_id, generation) -> underlying identity}` map and `{context_id -> rotation count}`.

**Invariants**

1. One request resolves exactly one immutable snapshot object. A snapshot is a frozen dataclass;
   a switch cannot reach into an already-resolved one, so in-flight rebinding is impossible by
   construction rather than by discipline.
2. A session switch advances **only that session's** generation. No other session and no instance
   default is touched.
3. Generation is monotonic per context. A rotation is never undone by a later steady-state
   resolution (`_rotations` offset).
4. Expired / unknown / pre-restart bearers are indistinguishable in the response, so the store is
   not a bearer oracle. All three fail closed with `reselection_required`.
5. The raw bearer never enters a snapshot, a log, a receipt, or a cache key.
6. The selection stores no action, write class, or permission.

**The subtle transition, stated explicitly.** The resolver must rotate on drift *underneath* a
generation, but must **not** double-count a deliberate switch that the store already accounted
for. That is why the drift map is keyed on `(context_id, generation)` rather than `context_id`:
a switch mints a new generation and therefore a fresh key, so no prior identity exists to compare
against. The drift identity also excludes the `generation=` component itself, because comparing a
value we are about to bump would answer its own question.

**Concurrency posture.** V1 selection is ephemeral and process-local
(`Restart / Durability Posture` in the task spec), so there is no cross-process state — but the
store *is* shared across threads, because FastAPI runs sync handlers in a thread pool. Every
mutation is a read-modify-write, so a `threading.RLock` serializes prune, create, inspect,
replace, and clear. Without it a PUT could read a record, lose the race to a concurrent DELETE,
and write the replacement back over the deletion, resurrecting a bearer reported as cleared;
two concurrent PUTs could also both publish the same generation. Pinned by
`test_concurrent_store_mutations_are_serialized`. Two concurrent *sessions* remain isolated for
a separate reason: separate keys and separate immutable records.

**Deny path.** `resolve()` invalidates the denied selection itself (dropping it from the
store via the injected `invalidate_selection` hook) and attaches a `CacheInvalidationDescriptor`
to the raised `BindingAuthorizationError`, so a denied selection cannot survive because a caller
forgot to invalidate.

**Bounded state.** `_last_identity` pops the superseded `(context_id, generation)` key on
rotation, so it does not accumulate one entry per generation.

**Producers / consumers.**
- Producers: the four Companion endpoints only. The #2223 gate is a **router-level**
  dependency, so an unauthenticated caller is rejected before instance state is read.
- Consumers: `ActiveContextSelectionResolver`, which additionally reads registry truth and GOV.
- Recovery: none. A lost store is a legitimate state (restart), and its consequence is a truthful
  reselection-required error, never a silent fallback.

---

## GOV interaction (all three mechanisms)

`BindingAuthorizer.authorize` is called once per binding per resolution, with `action`,
`write_class`, and `required_permission` supplied by the *caller's* endpoint contract. A deny
raises `BindingAuthorizationError` before any snapshot is constructed, so no `ActiveContextSet`
containing a denied binding is reissued, and a many-binding set never returns partially.
